# ЛУВР: продолжительность состояния и индикация

Выполнено 02.10.2026 как дополнение к этапу 5. Рабочая вкладка «ЛУВР» обновлена. Миграций и изменений структуры БД нет. Excel не формировался.

## Реализованное поведение

В строке месячного ЛУВР добавлена колонка «Состояние»: вахта или МВ, накопленные дни и индивидуальный максимум, текстовый статус и цвет. По нажатию открываются дата начала, контрольная дата, продолжительность, максимум, процент, активные согласованные исключения с датами и комментариями, периоды болезни и предупреждения истории.

Продолжительность отделена от календарных значений и месячных итогов. Календарь, состав месяца и четыре существующих totals не изменены. Смена контрольной даты влияет только на блок duration.

Для OBJECT + SHIFT и OFFICE + SHIFT используются те же подтверждённые movements и состояния `CalendarTimeline` этапа 4. Берётся последнее событие не позднее контрольной даты, включая историю до начала месяца/года. Дата ARRIVAL — первый календарный день ON_SHIFT; дата DEPARTURE — первый календарный день OFF_SHIFT. Значение ячейки FULL/HALF/TRAVEL не влияет на этот счётчик. Поездка до ARRIVAL не включается в новую вахту. Override, в том числе ручной DISMISSED, не меняет movement state и продолжительность.

Повторные события одного типа обрабатываются по последнему подтверждённому событию, как указано в задании; предупреждение о последовательности сохраняется в деталях. Противоположные события в одинаковое время дают UNKNOWN, без выбора по ID и без выдуманного нулевого счётчика. Историческая контрольная дата игнорирует последующие события.

## Контрольная дата

API принимает явный `as_of_date`. В интерфейсе есть поле «Состояние на дату»; пустое поле означает автоматический выбор. При смене месяца/года ручная дата сбрасывается. Эффективная дата всегда показана над таблицей.

- Прошлый месяц: последний календарный день месяца.
- Текущий месяц: текущая дата Asia/Yekaterinburg.
- Будущий месяц: текущая дата, без начисления ещё не прошедших дней.
- Явная дата может отличаться от выбранного месяца. Явная будущая дата разрешена для аналитики, возвращает `is_projection=true` и обозначается в UI как «Прогноз по известной истории». Она не выдаётся за фактически прошедший период.

## Болезнь, максимумы и исключения

Из включительного календарного интервала вычитается объединение пересекающихся периодов болезни. Открытый больничный ограничивается контрольной датой; даты за пределами состояния не вычитаются. Пересечения не считаются дважды. Movement state и начало периода сохраняются; после болезни счётчик продолжается.

На больничную дату `is_sick=true`, `indicator_enabled=false`, `indicator_status=NONE`. UI показывает «Болеет · индикация отключена» и накопленные дни, без предупреждающего цвета и порогового процента. Числовой ratio в API остаётся диагностическим. Исключения сохраняются и доступны в деталях.

Максимум выбирается из `max_shift_days` или `max_off_shift_days`. Значения по умолчанию не вводились. При NULL продолжительность считается, ratio=NULL, обычная индикация NONE.

| Продолжительность | Статус |
|---|---|
| меньше 50% | NORMAL / Норма |
| от 50% до 100%, не включая 100% | WARNING_50 / 50% срока |
| ровно 100% | MAX_REACHED / Максимальный срок |
| больше 100% | EXCEEDED / Срок превышен |

Порог проверяется целыми числами (`duration * 2 >= maximum`), без округления процента.

Активное исключение соответствующего типа SHIFT/OFF_SHIFT, включительно между date_from и date_to, заменяет индикацию на APPROVED_EXTENSION. Продолжительность, максимум, календарь и movements не меняются. На следующий день после date_to действует обычный порог. При нескольких действующих исключениях API возвращает все; основным выбирается исключение с наиболее поздним окончанием, затем началом и ID. Даже без максимума согласованное исключение может отображаться как отдельный информационный статус, без процента.

Для FIVE_TWO/неизвестного графика duration не рассчитывается (`NOT_APPLICABLE`). UNKNOWN возвращает null, а не 0/max. Начиная с dismissal_date статус DISMISSED, счётчики null и индикация отключена; дата до увольнения доступна для исторического расчёта. Архивирование не блокирует исторический расчёт.

## API

Расширен существующий GET, новый маршрут не нужен:

```text
GET /api/luvr/month?year=2026&month=10&as_of_date=2026-10-10
```

В `item` добавлены `as_of_date` и `is_projection`. В каждой строке `employees[]` добавлен `duration`:

```json
{
  "current_state": "ON_SHIFT",
  "state_since": "2026-09-20",
  "as_of_date": "2026-10-10",
  "current_duration_days": 21,
  "current_shift_days": 21,
  "current_off_shift_days": null,
  "max_shift_days": 30,
  "max_off_shift_days": 14,
  "maximum_days": 30,
  "ratio": 0.7,
  "indicator_status": "WARNING_50",
  "indicator_enabled": true,
  "is_sick": false,
  "active_exception": null,
  "active_exceptions": [],
  "sick_periods": [],
  "excluded_sick_days": 0,
  "movement_id": 1,
  "warnings": []
}
```

Пример иллюстративный, не новая запись в рабочей БД. Неверная дата возвращает 422. GET остаётся read-only. Максимумы и исключения загружаются общим SELECT вместе с фактами календаря, без дополнительных запросов на каждого сотрудника. Типизированные schemas опубликованы в Swagger.
