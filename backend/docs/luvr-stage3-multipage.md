## Parser и маршруты

Файловая точка входа `parse_rail_document(data, filename)` возвращает `list[ParsedRailTicket]`. Каждый результат содержит исходное `full_name` (также доступное как `full_name_raw`), собственные станции и datetime, имя исходного файла, `source_page`, `source_sha256`, статус и ошибки. Совместимый одностраничный helper сохранён для существующих вызовов и тестов; upload использует коллекцию.

Обнаружен один визуальный формат купона, но два способа упаковки: отдельный купон и несколько самостоятельных купонов по страницам. Для каждого сначала проверяется заголовок, затем применяется тот же проверенный parser купона. Новые неподтверждённые визуальные форматы и произвольные fallback-регулярки не добавлялись.

Дата, время и станция определяются относительно уникального маркера «Отправление по» / «Прибытие по» соответствующего блока. Порядок строк в потоке PDF не используется как порядок маршрута. Извлечение сохраняет подтверждённую двухколоночную геометрию этого макета; не заявляется поддержка любых сдвигов и произвольных версток. ФИО соединяется из строк своего блока, дубли рисования текста удаляются по совпадению текста и положения. Контрольная строка маршрута не используется для подстановки недостающих фактов.

Поле одной страницы никогда не заимствуется у другой. Если страница не содержит поддерживаемого купона, она получает отдельный `UNSUPPORTED` с причиной; неполный купон получает `PARSE_ERROR`. Ошибка страницы не отменяет остальные результаты. Формат одного билета, продолжающегося на следующей странице, не поддерживается автоматически.

Фильтр Салыма, exact employee matching, архив и автоматическое направление применяются **к каждому билету отдельно**. Даже внутри одного файла не предполагается одинаковое ФИО пассажиров. Отсутствующие данные не угадываются. Неполный маршрут не считается маршрутом без Салыма и не создаёт событие.

## Хранение и дубли

`rail_tickets` по-прежнему хранит конкретный билет. Миграция **008_rail_ticket_pages.sql** добавила nullable-поля `source_page` и `source_sha256` без изменения старых значений.

- `source_sha256` — SHA-256 исходного PDF; одинаковый у страниц одного документа.
- `source_page` — номер страницы, начиная с 1.
- Существующее уникальное поле `file_hash` сохраняется для совместимости как fingerprint билета. Для одностраничного документа это прежний SHA-256 всего файла. Для многостраничного — `SHA256(b'rail-page-v1\0' + SHA256(file).digest() + ASCII(page_number))`.

Таким образом, один PDF Каньшина создаёт две записи с разными fingerprints и общим source SHA. Повторная загрузка тех же байтов, в том числе под другим именем, возвращает обе существующие записи. Подтверждённые возвращаются как дубли, неподтверждённые сохраняют возможность продолжить обработку. Изменение содержимого PDF или экспорт страницы в новый файл считается новым источником: межфайловый семантический dedup этим исправлением не заявляется.

Старые fingerprints и связи подтверждённых билетов не изменены. У старых записей новые поля остаются NULL; автоматически переписывать их при миграции не требовалось. `employee_movements.source_file` хранит исходное безопасное имя, конкретная страница определяется через связь с `rail_tickets`.

Каждая карточка имеет отдельные Confirm/Reject. Подтверждение одной не подтверждает другую. Атомарность одного ticket → одного movement и защита от повторного Confirm сохранены.

## UI и API

POST `/api/rail-tickets/upload` возвращает прежний `items`, но теперь результатов может быть больше, чем входных файлов. Response schema дополнена `source_page`, `source_sha256`, `full_name_raw`. GET ticket возвращает эти же данные.

Карточка показывает исходное имя файла, номер страницы, исходное ФИО, оба конца маршрута с местным временем, автоматический заезд/выезд и собственное подтверждение. Неполные поля и причины ошибки отображаются отдельно. Нормализация ФИО нового сотрудника остаётся только предзаполнением формы; исходник билета не переписывается.

Статистика различает число выбранных файлов и количество разобранных билетов. Для двух новых PDF показывает два файла и три разобранных билета.

## SQL миграции 008

Явный запуск: `.\.venv\Scripts\python.exe -m app.database.migrate_rail_ticket_pages`. Runner выполняет транзакцию, advisory lock `(20261002,8)`, timeout блокировки 5 секунд и statement timeout 60 секунд. Старые миграции не изменены.

```sql
ALTER TABLE rail_tickets ADD COLUMN IF NOT EXISTS source_page INTEGER;
ALTER TABLE rail_tickets ADD COLUMN IF NOT EXISTS source_sha256 CHAR(64);
DO $$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conrelid='rail_tickets'::regclass AND conname='ck_rail_source_page') THEN
        ALTER TABLE rail_tickets ADD CONSTRAINT ck_rail_source_page CHECK(source_page > 0);
    END IF;
    IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conrelid='rail_tickets'::regclass AND conname='ck_rail_source_hash') THEN
        ALTER TABLE rail_tickets ADD CONSTRAINT ck_rail_source_hash CHECK(source_sha256 ~ '^[0-9a-f]{64}$');
    END IF;
END;
$$;
```

Исправление предоставленных случаев завершено. Диагностика отсутствующего исходника Елисеева остаётся отдельным неподтверждённым случаем. Переход к следующему этапу не выполнялся.
