## Среда и границы

Собственный временный PostgreSQL 18, отдельные stage3/stage37-копии с существующими DK/identity-триггерами. Исходный reconcile исполнялся ограниченной ролью фикстур по ранее разрешённой модели сравнения; новый протокол — кандидатом без прямых UPDATE/DELETE ДК. Фикстуры готовит отдельная ограниченная роль. Рабочие привилегированные реквизиты доступны только supervisor для READ ONLY отпечатков. PUBLIC закрыт только в изолированном стенде.

Испытаны минимальные SQL-последовательности соответствующих операций с настоящими серверными триггерами. Это не полный вызов HTTP или репозиториев: парсер PDF, _view, sync назначений, авторизация и построение ответа в конкурентные пары не входят. Причина установлена для конкретного порядка захвата ресурсов; полные пользовательские цепочки и частота конфликтов требуют отдельной проверки.

Источники: repositories/rail_tickets.py: _ticket, store_parsed_ticket (строка 135), set_ticket_object (247), предварительный FOR SHARE сотрудника (36/214); repositories/crew_memberships.py: FOR UPDATE перед UPDATE (15); реальные identity/DK-триггеры восстановленной схемы. Новый aaa_tx_dk_guard также берёт DK до изменения источника. Эти производственные модули и протокол не менялись.

## Синхронизация и пределы

Два соединения-актора, отдельный наблюдатель pg_locks и Python Event. Держатель сначала берёт identity либо строку сотрудника. Писатель выполняет DML, получает DK и блокируется на ресурсе держателя. Наблюдатель фиксирует ожидание и открывает gate; держатель выполняет DML, запрашивая DK и замыкая цикл.

lock_timeout=4 с, statement_timeout=8 с, connect_timeout=3 с; SHOW deadlock_timeout=1s. Ожидания Event ограничены 5 с, наблюдение — 2,5 с, join — 11 с с аварийным cancel при необходимости. Все акторы завершились, аварийный cancel не понадобился. Глобальные настройки не менялись.

Снимки pg_locks записаны перед gate. Для ticket_identity писатель держит ExclusiveLock DK(20261017,29) и ждёт ExclusiveLock identity(20261013,24), удерживаемый другим актором вместе с (20261007,1601). Для строковых случаев ожидание UPDATE видно как ShareLock на transactionid владельца строки; это не тот же термин, что SQL FOR SHARE. Серверный SQLSTATE 40P01 подтверждает цикл после gate, а не просто таймаут.

## Воспроизведённые сценарии

| Сценарий | Держатель A | Писатель B | Действие A после gate | Результат |
|---|---|---|---|---|
| ticket_identity | ticket(20261007,1601), identity24, FOR UPDATE другого билета | INSERT PARSED-билета: DK29, затем ожидание identity24 в row-trigger | UPDATE object_id своего билета с NULL на существующий объект, ожидание DK29 | Подтверждённый цикл identity/DK |
| crew_update | FOR UPDATE сотрудника | UPDATE ФИО: DK29, затем ожидание строки | UPDATE employees SET crew_id=crew_id, ожидание DK29 | Подтверждённый цикл строка/DK |
| share_cycle | FOR SHARE сотрудника | UPDATE ФИО: DK29, затем ожидание строки | INSERT employee_movements, ожидание DK29 | Подтверждённый цикл строка/DK |
| share_wait | FOR SHARE сотрудника | UPDATE ФИО: DK29, затем ожидание строки | COMMIT читающей транзакции без запроса DK | Обычное ожидание разрешилось, оба COMMIT |

crew_update использует повторный UPDATE того же crew_id: это минимальный эквивалент завершающего DML change_memberships, а не функциональный тест переноса экипажа. BEFORE STATEMENT срабатывает и без изменения значения. share_cycle воспроизводит механизм «FOR SHARE → календарная запись», встречающийся в билетной цепочке, а не всё подтверждение билета. Дополнительные lock полной цепочки могут дать иные расписания.

Подготовленная HTTP-политика запрещает массовый состав экипажа и подтверждение билета обеим ролям. Эти тесты прямого SQL не расширяют HTTP-права. Текущий 8001 пока без обязательной авторизации; подготовленные запреты нельзя выдавать за действующее ограничение сервера.

## Причина и рекомендация — без внедрения

Причина: один путь держит DK и запрашивает identity/строку, другой держит identity/строку и запрашивает DK. Ошибка воспроизводится до финальной криптографической проверки; изменение календарных правил или ослабление подписи её не исправит.

Предлагаемый для отдельного проектирования общий порядок: **DK(20261017,29) → ticket(20261007,1601), если нужен → identity(20261013,24), если нужен → строки в детерминированном порядке**. Он сохраняет ticket→identity, но требует брать DK до предварительных FOR UPDATE/FOR SHARE и identity во всех транзакциях, которые затем пишут календарь. Чистому читателю, который не запрашивает DK и не превращается в писателя, DK автоматически не предлагается.

Это архитектурный кандидат, не доказанный патч всего приложения. Нужно проверить все остальные advisory/row locks, FK, функции, ручные ДК и роли-писатели, включая identity-пути вне билетов. Перестановка одного SELECT не гарантирует общего порядка. Нельзя поздно превращать строкового читателя в DK-писателя с обратным порядком. При произвольном SQL одного соглашения Python недостаточно: обязательность порядка либо безопасный отказ требуют серверного проектирования.

Следующие изолированные проверки должны повторить те же расписания с предлагаемым порядком, полные билетные цепочки, FK/строковые взаимодействия, SAVEPOINT, SET CONSTRAINTS и все роли-писатели. Политика retry после deadlock отдельно требует идемпотентности и контроля файловых эффектов; автоматический retry не добавлен.

Подтверждены три описанных типа цикла. Другие сочетания production-assignment/identity/source lock и каскадов остаются потенциальными. Частота и исторические рабочие deadlock не установлены. Нулевые deadlocks шага 38 этому не противоречат: там менялось только ФИО без смешанного захвата ресурсов.
