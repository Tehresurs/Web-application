# Журнал: объекты / подобъекты, фильтры и история

Расширен существующий `GET /api/daily-control-results`. POST сохранения и проверки,
matching, aliases, Word-парсер, категории и назначения не изменены.

## Фильтры

| Параметр | Смысл |
|---|---|
| `date_from`, `date_to` | Обязательные даты, обе границы включены |
| `view=object` или `employee` | Порядок группировки, не ограничивает выборку |
| `employee_id` | Конкретный инженер; отсутствие — все |
| `object_id` | Основной объект |
| `subobject_id` | Конкретный подобъект |
| `include_subobjects` | При object_id включает подобъекты; по умолчанию true |

Default true сохраняет семантику прежних запросов object_id. Для самого основного
объекта укажите false: выбираются только строки с subobject_id IS NULL.
При subobject_id выбирается именно он; checkbox включения других подобъектов
не применяется. Если переданы оба ID, используются оба условия; несовместимая
пара возвращает пустой результат. Без object_id флаг include_subobjects не
ограничивает общую выборку. Значения ID должны быть положительными, «Все» не
передаётся как 0. Пустая выборка возвращает HTTP 200 и нулевые счётчики.

Примеры:

```text
# Все позиции и инженеры
/api/daily-control-results?date_from=2026-09-01&date_to=2026-09-30

# Только основной объект 5
/api/daily-control-results?date_from=2026-09-01&date_to=2026-09-30&object_id=5&include_subobjects=false

# Вся история объекта 5 с его подобъектами
/api/daily-control-results?date_from=2026-09-01&date_to=2026-09-30&object_id=5&include_subobjects=true

# Подобъект 12
/api/daily-control-results?date_from=2026-09-01&date_to=2026-09-30&subobject_id=12

# Инженер 17 в контексте подобъекта 12
/api/daily-control-results?date_from=2026-09-01&date_to=2026-09-30&employee_id=17&subobject_id=12&view=employee
```

## Ответ и интерфейс

Сохраняются `items`, `groups`, `summary`. Записи дополнены
`control_item_type`, `control_item_name`, `control_item_key`.
Ключи `object:15` и `subobject:15` различаются даже при одинаковом числовом ID.
Для подобъекта сохраняются ID/название родителя и исходный `source_file`.

Группа режима object теперь соответствует конкретной контролируемой позиции,
а не объединяет все подобъекты под одним названием. Пары «инженер + позиция»
содержат уникальные отсортированные `dates`, `days_count`, `fact_ids`.
В режиме employee группы соответствуют инженерам. `dates` верхнего уровня
показывает уникальные даты текущей отфильтрованной выборки.

`options.employees` и `options.control_items` — уникальные варианты за выбранный
период, независимо от остальных фильтров. В списке есть родитель, даже если
контролировались только его подобъекты. Неактивные подобъекты не скрываются из
истории. Если выбранная позиция отсутствует в новом периоде, UI сохраняет выбор
и показывает пустой результат, а не незаметно переключает фильтр на «Все».

Одна строка таблицы имеет пять основных колонок:
Дата | Инженер | Объект / Подобъект | ПО | Категория.
У подобъекта родитель показан небольшим справочным текстом. Исходный файл
доступен в раскрываемых деталях ячейки даты.

Нажатие на пару раскрывает уникальные даты и факты. ФИО в таблице и заголовке
инженера открывает его историю, сохраняя выбранную позицию, период и режим
включения подобъектов. Название позиции открывает её историю, сохраняя инженера.
Для конкретного фильтра пары раскрываются автоматически. Переключение режима
меняет порядок фильтров и группировки. Начальный период остаётся текущим месяцем.

## Контрольный пример из изолированных тестов

Данные: 8 фактов, 2 основных объекта, 3 подобъекта, 2 инженера, 5 разных дат.
У объекта 1: основной факт, подобъекты A и B; разные ПО могут дать несколько
фактов на одну дату. У объекта 2: основной факт и подобъект C.

- Все позиции: основных объектов 2, подобъектов 3, инженеров 2, фактов 8.
- Объект 1 без подобъектов: 1 факт.
- Объект 1 с подобъектами: 6 фактов, 1 основной объект, 2 подобъекта.
- Подобъект A: 4 факта, 2 инженера, 3 дня контроля.
- Инженер 1: уникальные даты 03.09.2026, 04.09.2026, 11.09.2026, 18.09.2026.
- Инженер 1 + A: даты 03.09.2026 и 04.09.2026; 3 факта из-за разных ПО,
  но всего 2 дня контроля.

Основные объекты считаются по distinct object_id, подобъекты — distinct
ненулевого subobject_id. Факты, позиции и дни не смешиваются.

## Запросы и производительность

Фильтрация выполняется PostgreSQL с параметрами и прямыми сравнениями ID/даты.
UI делает один GET для выбранных фильтров; не загружает вторую полную выборку
периода ради построения выпадающих списков. Для списков используются SELECT
DISTINCT в backend. Для раскрытия пар используются fact_ids, без повторной
фильтрации всех фактов на каждую пару в браузере.

Проверены существующие индексы report_date, (employee_id, report_date),
(object_id, report_date), subobject_id и уникальный индекс факта. EXPLAIN на
текущих 39 строках выбирает Seq Scan; это ожидаемо для маленькой таблицы.
Диагностическая проверка с SET LOCAL enable_seqscan=off подтвердила доступность
индексных планов для всех четырёх условий. Настройки БД и индексы не изменялись.

Новые миграции не нужны. Структура факта неизменна:
**Дата + Инженер + Объект / Подобъект + ПО + Категория**.
