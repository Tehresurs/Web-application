# Объект при заезде → производственное назначение

11.10.2026.

## Причина

`set_ticket_object()` сохранял только `rail_tickets.object_id`, а `confirm_ticket()` создавал движение, но не вызывал существующий writer датированных назначений. `project()` и матрица корректно читали назначения, однако записи для выбранного в билете объекта отсутствовали.

## Исправление

Подтверждение заезда, выбор/смена объекта подтверждённого билета и восстановление вызывают общий адаптер `rail_production_assignments.sync()`. Он использует существующий `production_assignments.save()` в той же транзакции и под существующей advisory-блокировкой. Ошибка назначения откатывает изменение билета и движения.

Назначение связано с билетом и идентификатором движения заезда; сохраняются версии источника и периода. Повторное подтверждение не создаёт дублей. Изменение основного объекта сохраняет остальные объекты набора и историю исправления. Независимое назначение на ту же дату не перезаписывается: совпадающий объект сохраняется как есть, несовпадающий вызывает явный конфликт.

Аннулирование выключает применимость через прежний `project()`, восстановление возвращает её. Снятие объекта с билета также выключает прежнее назначение по версии источника, не удаляя историю. Новый заезд получает свой период. Плановые доли и начало доступной работы по-прежнему определяет ЛУВР; FACT и дальнейшее наследование не изменены.

Frontend уведомляет существующие представления об изменении после подтверждения и выбора объекта. Дизайн не менялся.

## Проверки

- Backend: **458 тестов прошли**, включая 9 новых интеграционных тестов на изолированной PostgreSQL. Новый/существующий сотрудник, PLAN, приоритет FACT, несколько объектов, смена/снятие объекта, повторное подтверждение, убытие/новый заезд, аннулирование/восстановление, атомарный откат и защита независимого набора.
- Frontend: **192 теста прошли**, пропусков нет. Первоначальный запуск браузерного теста не смог подключиться к CDP; после запуска Chrome весь набор прошёл.
- Браузерный сценарий матрицы на изолированной БД: корректировки, наследование, FACT/PLAN, CAMERAL, конфликт, перезагрузка, навигация и три размера экрана — пройден, JS-исключений нет.
- У рабочих билетов 166 и 198 восстановлены две отсутствовавшие связи через тот же writer. Повторный запуск ничего не изменил. Сравнением проверена неизменность билетов, движений, подтверждённых фактов, сотрудников, должностей и состава ЛУВР.
- Рабочий API октября показывает объект 60 как PLAN: сотрудник 1 с 16.10 (0,50 по ЛУВР), сотрудник 11 с 13.10 (1,00). Доступность в день приезда не выдумывается адаптером.

## Ограничения

Билет передаёт только объект. ПО, подобъект, субподрядчик и категория не угадываются; режим берётся только из существующей политики значения по умолчанию. Недостающие реквизиты сохраняют предупреждения матрицы и заполняются через существующие механизмы назначения/корректировок. Обязательные данные для связи — подтверждённый билет заезда, сотрудник, движение, дата и выбранный объект; дополнительные ссылки проверяет прежний writer.

Для офисного графика существующая модель требует явного периода назначения: адаптер не создаёт вымышленный период ARRIVAL. Новый сотрудник отображается в матрице только после включения в состав соответствующего месяца ЛУВР. Старые изолированные схемы без таблиц этапа 3А сохраняют прежнее поведение билетов; рабочая схема содержит эти таблицы.
