## 3. Архитектура

```text
Выбор папки / выбор файлов / Drag & Drop
  → один multipart POST /api/rail-tickets/upload
  → валидация файла
  → отдельный PDF parser → ParsedRailTicket
  → SHA-256 + repository → сохранённый разбор
  → точное сравнение ФИО с employees
  → карточка результата
  → явный выбор «Заезд / Выезд»
  → явное подтверждение
  → одна транзакция: INSERT RAIL movement + связь с ticket
```

Использованы существующие FastAPI, UploadFile, PostgreSQL connection/repository, Pydantic и frontend без нового фреймворка. Parser возвращает структуру и не выполняет SQL. Поле папки использует `webkitdirectory multiple`: браузер передаёт файлы, backend не читает произвольный клиентский Windows-путь. Все три способа идут через один endpoint и одну функцию обработки.

## 4–5. Формат и извлекаемые факты

Поддерживается одностраничный незашифрованный PDF с текстовым слоем **типового контрольного купона РЖД предоставленного макета**. Проверены оба исходных файла из `C:\Projects\Билеты`:

| Файл | ФИО | Отправление | Прибытие |
|---|---|---|---|
| ЖД Аниськов В.И Салым-Сургут.pdf | АНИСЬКОВ ВЛАДИМИР ИВАНОВИЧ | Салым, 06.09.2026 07:32 | Сургут, 06.09.2026 11:12 |
| ЖД Петров А.В Тюмень-Салым.pdf | ПЕТРОВ АЛЕКСЕЙ ВЛАДИМИРОВИЧ | Тюмень, 10.09.2026 23:04 | Салым, 11.09.2026 07:29 |

Макет рисует некоторые надписи дважды с небольшим смещением. Parser убирает совпадающие фрагменты в одной позиции; повторяющиеся буквы в ФИО не удаляет. Координаты областей приведены к размеру образцов. Проверяются заголовок купона и подписи отправления/прибытия. OCR не используется. Скан, другой макет или неполные данные получают «Требует проверки» с причиной; универсальная поддержка любых билетов не заявляется.

Сохраняются только ФИО, две станции, два типизированных datetime, безопасное имя файла, fingerprint и состояние обработки. Паспорт, дата рождения, стоимость, вагон, место, номер заказа и QR в модель и БД не попадают. Нет постоянного файлового архива; UploadFile закрывается после запроса. Безопасные тестовые PDF содержат только необходимые текстовые области, а не копии оригинальных документов целиком.

Проверяются расширение и сигнатура PDF, структура, пустой файл и размер. Лимиты: 50 файлов, 10 МиБ на файл, 50 МиБ прочитанных данных на пакет. Ошибка одного файла возвращается отдельной карточкой и не отменяет остальные. Клиентское имя очищается от путей и недопустимых символов, не используется для записи файла на диск.

## 6–9. ФИО, FOUND / NOT_FOUND, архив

Нормализация: удаление внешних пробелов, схлопывание внутренних пробельных символов, `casefold()`. Не заменяются буквы, в том числе `ё` на `е`; сокращения, опечатки и другое отчество не исправляются. Fuzzy matching, aliases и нормализация ежедневных отчётов не вызываются — это отдельно проверено тестом.

Одно точное совпадение даёт `FOUND`, `employee_id` и имя из справочника. Отсутствие совпадения даёт `NOT_FOUND`; несколько одинаковых ФИО требуют проверки справочника и не позволяют создать событие. Сопоставление пересчитывается при чтении карточки и перед подтверждением; окончательная связь с сотрудником сохраняется вместе с movement.

Архивное точное совпадение отображается как «Сотрудник находится в архиве». Подтверждение блокируется; `is_archived`, `archived_at`, `dismissal_date` не изменяются. Пользователь может отдельно восстановить сотрудника штатным действием во вкладке сотрудников и нажать «Проверить сотрудника». При подтверждении сотрудник повторно проверяется и блокируется `FOR SHARE` до завершения транзакции, чтобы конкурентное архивирование/переименование не обошло проверку.

## 10–11. Создание сотрудника без повторной загрузки

«Создать сотрудника» открывает существующую форму с предзаполненным ФИО из билета. Все прежние поля и проверки формы остаются доступны. После успешного сохранения frontend запрашивает уже существующий ticket по ID: выполняется новое точное сравнение. Новый upload не нужен, что проверено по Network в Chrome.

Разбор хранится в `rail_tickets`, а карточки остаются в текущей сессии страницы. Отмена формы не удаляет разбор. После перезагрузки страницы отдельный список всех билетов пока не предусмотрен: повторная загрузка тех же байтов возвращает ту же сохранённую запись с прежним выбранным направлением, либо её можно получить API по ID.

## 12–14. Направление и RAIL movement

В существующей модели нет надёжной привязки станций к рабочему региону сотрудника. Поэтому направление всегда выбирает пользователь: **Заезд / Выезд**. Оно не выводится из времени, названия станции или назначений. Пока направление не выбрано, кнопка подтверждения отсутствует, API подтверждения возвращает 409.

После выбора отображается готовность к подтверждению. Только явное нажатие «Подтвердить» создаёт событие:

- `transport_type = RAIL`.
- `ARRIVAL`: `event_datetime = arrival_datetime`.
- `DEPARTURE`: `event_datetime = departure_datetime`.
- Обе станции и безопасное исходное имя сохраняются в существующих полях movement.
- `rail_tickets.movement_id` и `employee_id` фиксируют источник созданного события.

Время остаётся местным `TIMESTAMP WITHOUT TIME ZONE`, без UTC-конвертации. Клиент не может подменить employee_id, время или маршрут через endpoint подтверждения. Разбор, сотрудник, архивность и направление проверяются backend заново.

«Отклонить» сохраняет `REJECTED` без movement. Повторная загрузка отклонённого билета возвращает его состояние. Повторное открытие отклонённого билета для обработки отдельной функцией в этот этап не входило.

## 15–16. Дубли и таблица rail_tickets

Поле `source_file` этапа 2 недостаточно для fingerprint и незавершённого разбора. Поэтому добавлена отдельная таблица `rail_tickets`: факты разбора, SHA-256, ошибки, выбранное направление, статус и связь с событием. Байты документа в БД не сохраняются.

`UNIQUE(file_hash)` и `INSERT ... ON CONFLICT DO NOTHING` защищают загрузку. Незавершённый дубль возвращает существующий разбор; подтверждённый — «Билет уже обработан», сотрудника и созданное событие. Имя файла не определяет идентичность: переименование не создаёт второй ticket, одинаковые имена с разными байтами допускаются. Совпадение времени movement не является основанием для запрета другого билета.

Подтверждение блокирует ticket `FOR UPDATE`. INSERT события и UPDATE билета выполняются в одной транзакции; повторный или конкурентный Confirm возвращает уже созданный movement. Проверены три одновременные загрузки и три одновременных подтверждения через независимые соединения PostgreSQL: один ticket и один movement. Искусственная ошибка после INSERT полностью откатывает событие, билет остаётся неподтверждённым, соединение продолжает работать.

`UNIQUE(movement_id)`, FK `ON DELETE RESTRICT` и CHECK защищают связи. История не удаляется каскадно. Отдельное изменение или удаление события подтверждённого билета через общий API истории возвращает 409. Для SELF таких ограничений не добавлено.

Логи используют стандартный `logging`, как существующие backend-модули: `RAIL_FILE_ACCEPTED`, `RAIL_PARSE_SUCCESS/ERROR`, `RAIL_EMPLOYEE_FOUND/NOT_FOUND`, `RAIL_ARCHIVED_EMPLOYEE`, `RAIL_DUPLICATE`, `RAIL_MOVEMENT_CONFIRMED`. В этих сообщениях используются технические ID/размер, без полного текста PDF и паспортных данных.

## 17. Миграция и полный SQL

Источник: `app/database/migrations/007_rail_tickets.sql`. Штатный запуск из backend: `.\.venv\Scripts\python.exe -m app.database.migrate_rail_tickets`. Runner использует транзакцию, advisory lock `(20261002, 7)`, `lock_timeout = 5s`, `statement_timeout = 60s`. Повторное применение проверено тестом, старые строки сохраняются.

```sql
CREATE TABLE IF NOT EXISTS rail_tickets (
    id BIGSERIAL PRIMARY KEY,
    file_hash CHAR(64) NOT NULL UNIQUE CHECK (file_hash ~ '^[0-9a-f]{64}$'),
    source_filename TEXT NOT NULL CHECK (btrim(source_filename) <> ''),
    full_name TEXT,
    departure_station TEXT,
    departure_datetime TIMESTAMP WITHOUT TIME ZONE,
    arrival_station TEXT,
    arrival_datetime TIMESTAMP WITHOUT TIME ZONE,
    parse_errors JSONB NOT NULL DEFAULT '[]'::jsonb CHECK (jsonb_typeof(parse_errors)='array'),
    status TEXT NOT NULL CHECK (status IN ('PARSED','PARSE_ERROR','REJECTED','CONFIRMED')),
    employee_id BIGINT REFERENCES employees(id) ON DELETE RESTRICT,
    movement_type TEXT CHECK (movement_type IN ('ARRIVAL','DEPARTURE')),
    movement_id BIGINT UNIQUE REFERENCES employee_movements(id) ON DELETE RESTRICT,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT ck_rail_ticket_confirmed CHECK (
        (status='CONFIRMED' AND movement_id IS NOT NULL AND employee_id IS NOT NULL
         AND movement_type IS NOT NULL AND full_name IS NOT NULL
         AND departure_station IS NOT NULL AND departure_datetime IS NOT NULL
         AND arrival_station IS NOT NULL AND arrival_datetime IS NOT NULL)
        OR (status<>'CONFIRMED' AND movement_id IS NULL)
    )
);
CREATE INDEX IF NOT EXISTS ix_rail_tickets_employee ON rail_tickets(employee_id);
```

## 22. API и запуск

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/api/rail-tickets/upload` | multipart: повторяющееся поле `files`; результаты по каждому файлу |
| GET | `/api/rail-tickets/{ticket_id}` | сохранённый разбор и актуальное точное сопоставление |
| PATCH | `/api/rail-tickets/{ticket_id}/direction` | `{"movement_type":"ARRIVAL"}` или `DEPARTURE` |
| POST | `/api/rail-tickets/{ticket_id}/confirm` | `{}`; атомарное создание события |
| POST | `/api/rail-tickets/{ticket_id}/reject` | `{}`; отклонение без создания события |

Успех: HTTP 200, `{ "status": "ok", "item": { ... } }`; upload возвращает `items`. Пример части ответа подтверждения для первого билета в изолированном браузерном сценарии:

  "item": {

    "source_filename": "ЖД Аниськов В.И Салым-Сургут.pdf",
    "full_name": "АНИСЬКОВ ВЛАДИМИР ИВАНОВИЧ",
    "status": "CONFIRMED",
    "processing_status": "CONFIRMED",
    "match_status": "FOUND",
    "employee_id": 1,
    "movement_id": 1,
    "movement_type": "DEPARTURE",
    "movement": {
      "id": 1,
      "employee_id": 1,
      "movement_type": "DEPARTURE",
      "transport_type": "RAIL",
      "event_datetime": "2026-09-06T07:32:00",

Конфликт состояния: 409 с `status:error` и понятным `message`; отсутствующий ticket: 404; неправильные поля/enum: 422. В карточке ошибка одного PDF является `PARSE_ERROR` внутри успешного ответа пакета.

После перезапуска рабочий backend отвечает **200** на `/`, `/docs`, `/openapi.json`. Все пять новых маршрутов присутствуют в OpenAPI. HTTP 200 также получен для списков сотрудников (действующие/архив), должностей, экипажей, объектов, подобъектов, ПО, категорий, aliases, назначений сотрудника 25, Журнала за 2026 год и всех четырёх разделов истории сотрудника 25. Рабочая `rail_tickets` остаётся пустой: тестовые подтверждения в неё не записывались.
