# Этап 4 — расчёт Производственной матрицы

08.10.2026. Реализован единый read-only backend расчёта. Миграций нет, расчёт не сохраняет план или доли в БД. UI, Расстановка, АОС и экспорт не создавались.

## Файлы

- `app/repositories/production_matrix.py` — загрузка одного согласованного снимка БД.
- `app/services/production_matrix.py` — объединение календаря, интервалов назначений, фактов, корректировок; доли и проверки.
- `app/api/production_matrix.py` — GET endpoint.
- `tests/test_production_matrix.py` — расчётные и интеграционные тесты.
- `app/main.py` — только импорт/регистрация нового router в этом этапе.
- Этот отчёт.

## Источники и алгоритм

Состав строго из luvr_month_employees. Порядок как в месячном ЛУВР: нормализованное полное ФИО, затем employee_id. Фильтр employee_id не добавляет сотрудника в состав. Несформированный месяц возвращает formed=false и предупреждение, без создания записей.

Рабочее время — готовый FINAL существующего calculate_employee_month / CalendarTimeline. FULL=100 сотых, HALF=50, прочие коды=0. Сами календарные дни возвращаются без изменения, включая sickness, увольнение, ручные overrides и warnings.

Для назначений вызывается project этапа 3А; для категорий/режимов resolve этапа 3Б. Подтверждённый набор фактов дня приоритетнее плана. Факты вне известного периода не исчезают. Последующий план, ограничения периода, новый заезд и применимость билета определяются ранее реализованными сервисами.

Распределение выполняется в целых сотых. Объекты сортируются по object_id/subobject_id/po_id/subcontractor_id/id источника. Всем, кроме последнего, выдаётся целая часть available/count; последний получает остаток. Категория, название и экранная сортировка не меняют порядок распределения. Все суммы вычисляются по целым share_cents; share и share_text добавлены только для удобства отображения.

При рабочем времени и NO_OBJECT создаётся расчётная CAMERAL-строка. Категория отсутствует, report_required=false, редактирование запрещено. При UNKNOWN строка камеральной работы не создаётся. Объектная строка с отсутствующим ПО, категорией или режимом остаётся видимой и даёт WARNING. requires_daily_report управляет требованием объектного отчёта, без определения роли по названию должности.

FACT-корректировка меняет только день факта; PLAN-корректировки категории и режима независимы. edit_target содержит ключи и версии для API этапа 3Б. Наследуемая правка предыдущей даты не подменяет version новой правки выбранного дня. Источники с неизвестным периодом доступны только для чтения.

## Проверки дня

- object_cents — сумма объектных долей.
- cameral_cents — камеральное время отдельно.
- distributed_cents — сумма двух предыдущих.
- available_cents — доступное время ЛУВР.
- OK — распределение соответствует доступному времени без выявленных проблем.
- WARNING — неизвестное/неполное назначение, нераспределённое время или диагностическое предупреждение ЛУВР.
- CONFLICT — факт на нерабочий день, факт вне достоверного периода, неоднозначный календарь, пересечение периодов либо превышение времени.

Нерабочий факт сохраняется в ответе с исходными идентификаторами и share_cents=0, status=CONFLICT. Нулевое равенство сумм не скрывает конфликт. Доля рабочего времени не выдумывается. При отсутствии рабочего времени обычные плановые/камеральные ячейки не создаются.

## API

`GET /api/production-matrix?year=2026&month=10[&employee_id=2]`

Обёртка `{status: "ok", item: ...}`. Ответ item:

- year/month/formed;
- employees: employee_id, full_name, position_id/name, requires_daily_report, work_location/work_schedule;
- luvr_days: полный существующий результат календаря;
- rows: устойчивый row_key, объектная/камеральная строка и cells по датам;
- каждая cells содержит долю, источник FACT/PLAN, объект/подобъект/ПО/субподрядчика, категорию/режим, данные сотрудника, дату, исходный файл/ID, основание и период, edit_target, статус и warnings;
- checks: контрольные суммы и статус каждой даты;
- totals сотрудника и всего ответа, в сотых рабочего дня; working_days — количество рабочих дат сотрудника, в общем итоге сумма сотруднико-дней;
- source_warnings: диагностика исходных периодов.

Для единой согласованности производственное чтение выполняется в REPEATABLE READ READ ONLY. Источники читаются через существующие загрузчики календаря и назначений, без внутренних HTTP-вызовов.

## Ограничения

Для исходных Word-файлов в проекте нет готового URL загрузки: source_file и source_fact_id доступны, source_document_url=null. Неполные исторические назначения и невыбранные режимы не заполняются автоматически. Требование отчёта и наличие факта возвращаются раздельно; новый механизм контроля сроков сдачи отчётов не вводился.

Доступность времени полностью следует текущему ЛУВР. Отсутствия OTHER, не участвующие в действующем календаре, не вводятся в расчёт отдельным правилом. Интерфейс и экспорт матрицы остаются вне этапа.
