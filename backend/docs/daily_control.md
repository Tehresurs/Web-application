# Журнал контроля: БД и API

В блоке «Результат парсинга», рядом с выгрузкой HTML и Excel, подключена кнопка
«Сохранить результат». Она сохраняет весь текущий набор независимо от фильтров
таблицы и активна только после локальной и серверной проверки всех отчётов.
Запись выполняется только по нажатию; проверка готовности, парсинг папки
и чтение журнала ничего не сохраняют. После записи кнопка показывает
«✓ Результат сохранён» и блокируется. При ошибке сохранение набора останавливается:
уже записанные отчёты сохраняются, повторная проверка и попытка продолжают с
оставшихся. Каждый отдельный отчёт сохраняется атомарно.

Вкладка «Журнал контроля» показывает сохранённые факты. По умолчанию выбран
текущий месяц, все объекты и все инженеры. Доступны произвольный период и кнопки
«Сегодня», «Текущий месяц», «Текущий год». В режимах «От объекта» и «От инженера»
меняются порядок фильтров и группировка. Раскрытие строки с ФИО показывает
конкретные даты и таблицу ПО, категорий и исходных файлов. При каждом открытии
вкладки данные загружаются заново, поэтому видны недавно сохранённые результаты.

## Миграция

Из `backend` с настроенным `.env`:

```powershell
.venv/Scripts/python.exe -m app.database.migrate_daily_control
```

Скрипт применяет `app/database/migrations/001_daily_control_results.sql` одной
транзакцией. Существующие справочники и назначения не изменяются. Повторный запуск
допустим. Требуются `employees`, `construction_objects`, `po_types`,
`object_categories`, `employee_assignments`.

Факт: `report_date`, `employee_id`, `object_id`, `po_id`, `category_id`,
`source_file`, `created_at`. Дополнительно хранится SHA-256 исходного DOCX для
определения повторно открытого файла, в том числе после переименования.
Уникальность `(report_date, employee_id, object_id, po_id, category_id)` защищает
от повторной записи того же факта из другого файла. Первый исходный файл сохраняется.
Внешние ключи запрещают удалять справочники, на которые ссылается история.
Изменение/удаление назначения впоследствии не удаляет факт контроля.

## Проверка и ручное сохранение

`POST /api/daily-control-results/check` и `POST /api/daily-control-results`
принимают одинаковый JSON:

```json
{
  "path": "C:/Reports/report.docx",
  "employee_id": 12,
  "object_id": 34,
  "general_contractor_id": 5,
  "subcontractor_id": 6,
  "assignments": {"5": 101, "6": 102}
}
```

Обязателен только `path`. Остальные поля — окончательный выбор пользователя
после согласования. При их отсутствии сервер использует только точное совпадение
`found`. `assignments` связывает ID ПО с ID назначения, а не с категорией.
Если для связки существует ровно одно назначение, сервер выбирает его сам;
при нескольких требуется явный выбор. Категория берётся из назначения в БД.
Неизвестные поля, включая клиентские `can_save` и `report_date`, отклоняются.

Сервер читает неизменяемый снимок файла и повторяет разбор и сопоставление.
Дата берётся из результата парсера, а не из системного времени или запроса.
Для готовности нужны все обязательные поля парсера, окончательные ID инженера,
объекта и каждого указанного ПО и полное действующее назначение с категорией.
Явный выбор ID считается разрешением замечания только при наличии подходящего
назначения и всех справочных записей в БД. Пустое/неоднозначное/удалённое назначение
блокирует запись. Замечания вычисляются заново, клиентский список не используется.

При генподрядчике и субподрядчике создаётся по одному факту на каждое уникальное
ПО. Одинаковое ПО не дублируется. Весь отчёт сохраняется одной транзакцией.

Проверка возвращает `can_save`, `saved`, `report_date`, `source_file`, `problems`,
`facts`. Если есть замечания, `can_save=false`. Сохранение повторяет проверку
в своей транзакции и при замечаниях возвращает HTTP 409 с описанием в `detail`.
Успешное сохранение возвращает `saved=true`, `can_save=false`, `created` и
`results: [{"id": 123, "created": true}]`. Повторный запрос идемпотентен:
возвращает существующие ID с `created=false`. Уже сохранённый исходный файл
нельзя этим API перепривязать к другим сущностям.

Для кнопки: проверка → `can_save` → явное нажатие → сохранение →
`saved=true` → «✓ Результат сохранён». Автосохранения нет.

## Согласование отсутствующих организаций

В окне проверки отсутствие ПО и субподрядчика согласуется отдельно. «Согласовать
отсутствие» действует только для исходного отчёта (его SHA-256), а «Принять как
правило» — для всех последующих отчётов с отсутствующим значением этого поля.
Правила включаются независимо по каждому полю и отменяются через
`DELETE /api/daily-control-results/absence-rules/{field}`; отмена правила не
снимает отдельные согласования отчётов.

Согласованное отсутствие ПО остаётся `NULL`: название не подставляется из
назначения, а факт связывается с назначением сотрудника и `entity_id`, у которого
`po_id IS NULL`. В `daily_control_results` внешний ключ `po_id` сохраняется;
уникальное ограничение с `NULLS NOT DISTINCT` не допускает дублей таких фактов.
Миграция `025_report_review.sql` намеренно ограничена существующей тестовой схемой
`ai_excel_agent_test.test_construction_identity_stage46`; её нельзя запускать на
`public` или использовать как миграцию производственной БД.

## Чтение журнала

```text
GET /api/daily-control-results?date_from=2026-09-01&date_to=2026-09-30&view=object
GET /api/daily-control-results?date_from=2026-01-01&date_to=2026-12-31&view=employee&employee_id=12
GET /api/daily-control-results?date_from=2026-09-01&date_to=2026-09-30&employee_id=12&object_id=34
```

Границы включаются. Не переданный `employee_id` означает «Все инженеры»,
не переданный `object_id` — «Все объекты». Фильтры работают совместно.
`view=object` группирует по объекту, `view=employee` — по инженеру.
Одна выборка поддерживает день, месяц и год через границы периода.

Ответ содержит исходные `items`, `summary` (число фактов, объектов, инженеров,
уникальных календарных дней) и `groups`. В каждом элементе группы есть пара
инженер–объект, уникальные отсортированные `dates` и `days_count`.
Несколько ПО/категорий в один день дают один день контроля этой пары.
Запрос с обоими ID позволяет показать даты по нажатию на ФИО.
На этом этапе возвращается весь выбранный период; пагинация и «Приложение 7»
не входят в реализацию.

## Проверки

```powershell
$env:DAILY_CONTROL_TEST_DB = '1'
.venv/Scripts/python.exe -m unittest discover -s tests -v
node --test tests/test_report_save.cjs
node --test tests/test_journal.cjs
```

Интеграционные тесты создают изолированную схему PostgreSQL в транзакции и
откатывают её целиком. Боевые справочники/факты не используются как тестовые данные.
Без переменной окружения проверки PostgreSQL пропускаются.
