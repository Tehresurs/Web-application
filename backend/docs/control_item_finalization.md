# Этап 6: окончательный факт контроля

Бизнес-структура сохранена: **Дата + Инженер + Объект / Подобъект + ПО + Категория**.
Родитель подобъекта — справочная информация и ключ существующего назначения,
а не шестое обязательное поле. `employee_assignments` не изменяется.

## Уникальность

Проверен PostgreSQL 18.6. До этапа 6:

```sql
UNIQUE (report_date, employee_id, object_id, po_id, category_id)
```

Этот ключ запрещал разные подобъекты одного назначения в одну дату.
Теперь фактически применяется:

```sql
UNIQUE NULLS NOT DISTINCT
    (report_date, employee_id, object_id, subobject_id, po_id, category_id)
```

Полный точный SQL находится в `app/database/migrations/003_control_item_unique.sql`.
Запуск: `.\.venv\Scripts\python.exe -m app.database.migrate_control_item_unique`.
Автоматического запуска при старте приложения нет.

Миграция транзакционная и повторяемая: берёт блокировку таблицы, проверяет версию,
дубли и пары object/subobject, строит новый уникальный индекс и только после
его успешного построения заменяет старый constraint с сохранением имени.
При ошибке или таймауте изменения откатываются. Старые миграции не переписаны.

При одинаковых дате, инженере, родителе, ПО и категории разрешены три записи:

| object_id | subobject_id | Смысл |
|---|---|---|
| 5 | NULL | Основной объект |
| 5 | 12 | Подобъект A |
| 5 | 13 | Подобъект B |

Повтор любой из этих строк запрещён, в том числе строки с NULL.
Это 3 контролируемые позиции, 3 факта, но 1 основной объект.

## Источник и атомарность

`source_file` не входит в уникальность. Переименование и переупаковка Word
не создают новый факт при одинаковой бизнес-комбинации. Дубликат возвращает
ID и исходные реквизиты ранее сохранённой строки, `created: false`.

Сохранена прежняя семантика `source_sha256`: повтор того же содержимого Word
возвращает уже сохранённый результат без повторного согласования/перезаписи.
Один уже сохранённый исходный документ не используется для изменения истории
передачей других ID. Хеш вычисляется по тем же байтам, которые читает парсер.
Сохранение всех ПО одного отчёта идёт в одной транзакции; advisory lock
сериализует один источник, UNIQUE защищает одинаковый факт из разных источников.

Дата берётся только из Word: `report_date` нормализован в ISO YYYY-MM-DD,
`report_date_raw` сохраняет исходное написание. Backend повторно читает Word;
дату клиент передать не может. Некорректная/отсутствующая дата блокирует запись.

Backend проверяет реальные назначения, активность подобъекта и принадлежность
его родителю. Проверка пары также выполняется в repository перед вставкой.
Ожидающий сохранения или конфликтующий alias блокирует готовность; пользователь
может явно отказаться от запоминания и подтвердить выбор только для отчёта.
Автоматической перезаписи alias нет.

## Ответ API

Сохранён прежний контейнер `status`, `saved`, `created`, `results`.
Каждый элемент results теперь дополнительно содержит дату, инженера и имя,
объект, подобъект, фактически контролируемую позицию, ПО, категорию и источник.
Пример (условные ID):

```json
{
  "id": 101,
  "created": true,
  "report_date": "2026-09-24",
  "employee_id": 17,
  "employee_name": "Иванов Иван Иванович",
  "object_id": 5,
  "subobject_id": 12,
  "control_item_name": "Подъезд к кусту №55",
  "control_item_type": "subobject",
  "po_id": 3,
  "category_id": 2,
  "source_file": "report.docx"
}
```

Для основного объекта `subobject_id: null`, `control_item_type: object`,
`control_item_name` — название объекта. При дубликате возвращается та же запись
с `created: false`; UI показывает «Этот результат уже сохранён» и блокирует кнопку.

39 исторических фактов и 83 назначения сравнены с исходным снимком при применении
миграции: данные сохранены без изменений. Рабочая БД не заполнялась примерами;
тестовые факты создаются в изолированных схемах с откатом.

Эта миграция снимает ограничение, описанное в документе этапа 5
`subobject_review.md`; описание там фиксирует состояние предыдущего этапа.
