# Перемещение сотрудников — границы изменения по новому ТЗ

Дата: 20.10.2026. Проект C:/Projects/excel-ai-agent-8001.
Основание: приложение fd758a00-99bd-4fce-b9e2-a7263ccc2894/Вставленный текст.txt.
Статус: предложение для согласования структуры БД; новая реализация И.О. и рабочая миграция не выполнялись.

## Проверенная исходная реализация

В исходниках уже есть единый personnel_transfers API, репозиторий, окно employee_transfers.js и подготовленная миграция 033. Она хранит наблюдение исходной должности, версии справочника, события постоянного перевода, версии сотрудника и журнал идемпотентности. Это не рабочая установка: согласно предыдущей проверке миграция на рабочей БД отсутствует. В текущем чтении исходников нет структуры временных назначений. Сервис personnel_positions является заготовкой датированного чтения; реальные читатели ЛУВР, матрицы, Расстановки и ВОУ ещё не подключены. Флаги готовности ДК и датированных читателей по умолчанию запрещают кадровую запись.

## Минимальное предлагаемое изменение

Не создавать вторую карточку, справочник, параллельный API или историю основных должностей. Расширить существующее окно до «Перемещение сотрудников»: выбор существующего сотрудника, переключатель постоянного перевода/И.О., условные поля периода, общий журнал. Табельный номер показывать только из существующего достоверного поля, не подменять внутренним id.

Сохранить основную историю из 033. Добавить одну отдельную таблицу событий временных назначений personnel_acting_events: employee_id, root_id, revision, вид CREATE/CHANGE_END/END/CANCEL, position_id, starts_on, ends_on включительно, reason, actor_user_id, recorded_at. Конкретные SQL-типы, FK и ограничения должны быть проверены на восстановленной копии перед рабочей миграцией. Действующие назначения получать из последней ревизии каждого root_id; первоначальные и исправленные записи не удалять. Не записывать временную должность в employees.position_id. Использовать существующие состояние версии сотрудника и журнал request_id, распространив канонический payload на тип операции и период. Именованные операции ограничить фиксированными действиями, без произвольного SQL.

Проверять обязательные даты, начало <= окончание, существующие должности, активность сотрудника, актуальную версию, точные права действующей системы. Предлагается отклонять пересечение двух И.О. одного сотрудника; это правило требует согласования. Закрытие по дате вычислять при чтении, без фонового переписывания сотрудника. Досрочное завершение, изменение конца и отмена создают ревизию с основанием. Не передавать объекты автоматически.

## Интеграции без смены основных алгоритмов

Единый датированный кадровый адаптер должен возвращать основную должность и отдельное временное назначение. Постоянный перевод инженера СК в инженера ТА сохраняет одну строку сотрудника. Для И.О. Руководителя СК отдельная строка ЛУВР получает рабочее время периода; основная строка сохраняется, но те же рабочие дни не суммируются повторно. Отсутствия, движения, билеты и ротация не изменяются. Конкретное распределение кодов отображения и контроль итогов проверяются на существующем календаре, а не отдельным расчётом.

Матрица сохраняет факты, подтверждения и планы. На период согласованного И.О. адаптер обязательности отключает только инженерную ежедневную обязанность, не создавая ложного невыполнения. Не добавлять описания АОС/отчёта в матрицу. Расстановка и ВОУ используют дату строки/события и не дублируют человека. Сформированные подтверждённые документы не переписываются. Изменение, затрагивающее подтверждённый период, должно давать явный конфликт до согласования процедуры исправления.

Новые кадровые зависимости должны войти в проверяемый контекст ДК. Выставление флагов готовности не заменяет эту работу. Авторизацию, пользователей и роли не менять; недостающие рабочие учётные записи не создавать. Права на исправление/отмену И.О. необходимо сопоставить существующей политике до открытия кнопок.

## Порядок после согласования

1. Снять свежий READ ONLY снимок и хеши, сделать резервную копию и проверить восстановление.
2. На восстановленной копии проверить существующие поля, подготовить согласованное расширение 033 без применения к рабочей БД.
3. Расширить существующие именованные команды, репозиторий, API и окно; проверить повторы, версии и откат.
4. Подключить датированные адаптеры четырёх разделов и контекст ДК. Если потребуется изменение основных формул или структуры раздела — остановиться для отдельного согласования.
5. Проверить обе операции, границы дат, будущие/прошлые периоды, пересечения, историю после перезагрузки, отсутствие двойного учёта, сохранность фактов/планов и запреты доступа.
6. Представить результаты и план рабочего применения; не объявлять функцию работающей на 8001 по результатам отдельного стенда.

## Необходимые решения

- Разрешение на описанное расширение структуры БД (раздел 11 нового ТЗ требует предварительного согласования).
- Политика неизвестной истории до даты исходного наблюдения: прежний расчёт с явной пометкой либо запрет пересчёта до документального восстановления. Фиктивную дату начала не назначать.
- Разрешённые исполнители изменения конца/досрочного завершения/отмены И.О. без расширения действующих ролей; правило пересечений И.О.

В рамках этой сверки выполнены чтение приложения и исходников и запись настоящего документа. Новых тестов, запросов к рабочей БД, изменений схемы, перезапуска 8001 или внедрения не было. Ранее полученные результаты тестов не являются результатами нового ТЗ.
