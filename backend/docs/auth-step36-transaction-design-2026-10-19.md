## Точный инвариант

Пусть Dauto(T) — множество отметок, действительно удалённых автоматическим обслуживанием в транзакции T и не возвращённых откатом соответствующей подтранзакции. Пусть Sfinal(T) — окончательное состояние всех календарных источников в согласованной точке сериализации успешного COMMIT. Требование: для каждой d из Dauto(T) существующий eligible(Sfinal(T), d) = False. Эквивалентно, автоматическая очистка T не удаляет отметку, пригодную на её окончательных источниках.

Это гарантия сохранения, не требование создавать отсутствовавшие ДК. Она не запрещает законное изменение источника, делающее сотрудника непригодным, и не доказывает законность самого изменения через HTTP. Отдельное требование полноты: календарная пишущая транзакция не завершается успешно с пропущенным обязательным обслуживанием. Для конкурентных транзакций нужна согласованная сериализация, а не обещание неизменности календаря после любого будущего COMMIT.

## Что показывает текущий код

MatrixConnection.commit() вызывает _reconcile_dk перед super().commit(); ошибка приводит к rollback. transaction() вызывает его перед выходом из psycopg-контекста, в том числе при вложенных контекстах/SAVEPOINT. Поэтому выход из вложенного контекста не является доказательством окончательного состояния всей транзакции. Текущий флаг dirty — клиентский GUC, его нельзя использовать как границу безопасности.

matrix_dk.reconcile удаляет сразу и глобально проверяет существующие ДК. HMAC prepare вычисляет тот же eligible(), prune проверяет доказательство и немедленно удаляет. Последующее восстановление FULL не восстанавливает удалённую строку. Повторный reconcile эту проблему не решает.

## Сравнение

| Вариант | Произвольный SQL | Штатное поведение | Вывод |
|---|---|---|---|
| Только Python-проверка непосредственно перед COMMIT | raw COMMIT и промежуточные вызовы не контролируются БД | Минимальные изменения | Недостаточно |
| Только отложенный constraint trigger | SET CONSTRAINTS IMMEDIATE может вызвать очистку раньше | Обычно выполняется при COMMIT | Недостаточно без защиты после применения |
| Немедленная очистка и закрытая фаза SEALED | После удаления любые изменения источников отвергаются | Ломает продолжение работы после ранней очистки | Возможный строгий вариант |
| Подписанное намерение + отложенное применение + SEALED | Досрочное применение тоже закрывает дальнейшие изменения; raw COMMIT требует доказательства | Промежуточные вычисления не удаляют ДК; нужна новая подготовка после изменения | Рекомендуемый кандидат |
| Тот же канонический алгоритм в доверенной среде БД | Возможно независимо проверить пригодность при применении | Требует адаптации Python/соединений, не упрощённой SQL-копии | Отдельная архитектурная альтернатива |
| Worker после COMMIT | Не видит исходное незакоммиченное состояние | Теряется атомарность | Не соответствует цели |

PostgreSQL допускает досрочное выполнение deferred constraint triggers через SET CONSTRAINTS. Поэтому «отложенный» не означает «недоступный для раннего вызова».
Источники: https://www.postgresql.org/docs/18/sql-set-constraints.html и https://www.postgresql.org/docs/18/trigger-definition.html.

## Предлагаемый протокол

1. Обычные защищённые серверные триггеры на всех календарных источниках фиксируют изменения в закрытом транзакционном состоянии и организуют обязательную проверку завершения. GUC dirty может остаться только оптимизационной подсказкой. Записи создаются даже при прямом SQL и не зависят от вызова MatrixConnection.
2. Доверенный Python-компонент получает согласованный снимок, вызывает единственный eligible() и подписывает намерение. Служебный SQL только проверяет подпись и сохраняет намерение в закрытом журнале; ДК пока не удаляются. Подпись связывается с БД/версией протокола, транзакцией, защищённым nonce/ревизией, полным контекстом источников и ДК и точным каноническим списком. Нельзя использовать один лишь номер ревизии, повторно выдаваемый после SAVEPOINT, без проверки содержимого/защиты от повторного использования.
3. После изменений FULL/TRAVEL/HALF старое намерение становится непригодным. Штатный код перед внешним COMMIT заново рассчитывает и регистрирует решение. Вложенный transaction() не применяет очистку; окончательную проверку нельзя возлагать только на распознавание вложенности Python.
4. Обязательный серверный проверяющий механизм получает согласованные блокировки, проверяет текущий полный контекст и доказательство. Отсутствующее, повреждённое или устаревшее решение вызывает исключение, а не пропуск обслуживания. Автоматической подписи внутри SQL нет.
5. До удаления устанавливается закрытая фаза SEALED. Удаление и SEALED выполняются атомарно в том же серверном вызове. После этого обычные недеферрируемые триггеры отвергают изменение любого источника и изменение состава ДК, влияющее на заверенный результат. Кандидат не может сбросить фазу, изменить журнал, отключить триггеры, SET ROLE владельца или обойти их через функции/альтернативные таблицы.
6. Очистка исполняется один раз; повторные отложенные события проверяют закрытое состояние и не запускают рекурсивное обслуживание. Состояние после собственного удаления ДК должно учитываться отдельно: сравнивать исходный отпечаток ДК с уже изменённой таблицей нельзя. Нужны точные собственные удаления/постконтекст, а не широкое исключение из проверки.
7. Если SET CONSTRAINTS IMMEDIATE запускает применение раньше, оно либо отказывает без актуальной подписи, либо очищает и закрывает фазу. Последующий SQL изменения источника отвергается. Другие deferred triggers, выполняющиеся позже, тоже не могут изменить заверенные источники незаметно.

Без закрытой фазы пункт 7 возвращает обход шага 35. Отложенность уменьшает число ранних закрытий в нормальном сценарии, но не заменяет эту защиту.

## SAVEPOINT и ошибки

Закрытое состояние, намерения, очередь проверки и ДК должны быть обычными транзакционными данными с согласованной семантикой подтранзакций. ROLLBACK TO точки до применения возвращает и удаление, и SEALED; после него можно изменять источники и получать новое решение. Точка после применения сохраняет SEALED: изменение источника должно отвергаться. RELEASE SAVEPOINT не должен выполнять окончательную очистку внешней транзакции.

Откат изменений после регистрации намерения не гарантирует его пригодность автоматически: решение проверяется по текущему состоянию. Повторные FULL/TRAVEL/HALF допустимы до применения, но требуют финальной подписи. Подмена клиентского GUC, SET CONSTRAINTS DEFERRED, прямой COMMIT, повторный вызов служебных функций не должны убирать обязательную проверку.

При исключении во время COMMIT транзакция не должна фиксироваться: исходные INSERT/UPDATE и очистка откатываются вместе. Ошибка до COMMIT может быть обработана откатом к SAVEPOINT; успешное последующее завершение допустимо только после отката/устранения проблемного состояния и новой корректной проверки, а не с сохранённой устаревшей авторизацией. Недопустимо возвращать UI успешный результат записи до успешного COMMIT. При потере связи на COMMIT исход неопределён: сначала проверка результата, затем решение о повторе.

Файлы/Excel, печать и внешние действия PostgreSQL не откатывает; последовательности также могут иметь пропуски. Если рабочая цепочка создаёт файл до фиксации БД, отдельно требуется staging/публикация после успешного COMMIT и компенсация. Этот отчёт не объявляет существующий архив транзакционным и не меняет его.

## Полномочия и границы возможности

При совершенно неизменных текущих grants/триггерах/служебных функциях инвариант уже опровергнут шагом 35. Новый протокол потребует отдельно согласованных объектов служебной схемы и триггеров, но не прямых UPDATE/DELETE ДК приложению. Владелец службы — NOLOGIN, минимальные объектные права; приложение — только узкие входы, без прямого доступа к журналу. Старый немедленный prune не должен остаться альтернативным обходным входом.

Абсолютная гарантия против SQL-суперпользователя, владельца исходных таблиц, кражи HMAC-ключа или произвольного выполнения доверенного Python невозможна в этой модели. Рабочая текущая суперроль не является испытанной кандидатной ролью. Нужны ограниченные ACL, закрытые PUBLIC/TEMP/CREATE, запрет возможностей отключения триггеров/смены владельца и безопасный SQL-контекст подписывающего расчёта. Служебные SECURITY DEFINER должны использовать полные имена и фиксированный search_path. Устранение PUBLIC остаётся отдельным блокером.

Подпись доказывает доверенное вычисление только при полном наборе зависимостей eligible(), неизменном доверенном коде и согласованном снимке. Вызовы eligible и отпечаток не должны читать разные объекты из-за search_path или разное конкурентное состояние. Блокировки должны охватывать все разрешённые пути записи, включая FK/триггеры, и сохраняться до завершения транзакции. Наличие advisory lock само по себе не принуждает все пути его соблюдать. Поддержку изоляции кроме READ COMMITTED не добавлять без отдельного доказательства.

## Влияние и необходимость согласования

Календарные правила eligible() менять не требуется. Меняется транзакционная политика: после фактической очистки нельзя продолжать менять источники. До неё можно выполнять прежние промежуточные изменения. Транзакции без корректной финальной подготовки могут теперь завершаться отказом вместо прежнего COMMIT. Порядок видимости ДК внутри незавершённой транзакции также изменяется: при подготовке отметки остаются до применения. Это существенная совместимость, не скрытая техническая деталь.

Если требуется одновременно разрешить любые изменения после раннего удаления, не восстанавливать ДК, не переносить существующий алгоритм и не ограничивать SQL, гарантировать сохранность пригодных ДК нельзя. Нужно принять ограничение фазы либо проектировать иной механизм с независимой финальной проверкой и восстановлением/отложенным удалением. Без изменения модели транзакций готового минимального исправления нет.
