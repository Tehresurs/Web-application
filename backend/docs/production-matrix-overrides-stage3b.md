## Хранение и источники

Одна строка — изменение одного поля CATEGORY или CONTROL_MODE с effective_from, сотрудником, scope, period_key, basis_revision, версией и ссылкой на источник. Ручные режимы только INSPECTION/OPERATIONAL. CAMERAL вычисляется из NO_OBJECT этапа 3А, без ручных записей. CHECK исключает изменение двух полей одной строкой, некорректные значения и два источника одновременно. Уникальность учитывает NULL.

Источник — fact_id (FK RESTRICT) либо assignment_item_id (FK SET NULL). Во втором случае assignment_item_ref сохраняет исходный идентификатор после исправления/замены строки этапом 3А. Это ссылка происхождения, не копия исходных данных: потеря live FK делает корректировку неприменимой, история остаётся. Поэтому PATCH назначений не блокируется новой таблицей.

period_key берётся из существующего сервиса этапа 3А. Для PLAN basis_revision — версия основания плана (версия изменения набора или отпечаток полного набора фактов даты). Для FACT используется отпечаток только конкретного факта: добавление другого факта в тот же день не сбрасывает его индивидуальную правку.

DELETE логический: is_deleted=true и version увеличивается. Удалённая правка не участвует в расчёте. Это защищает от повторного создания устаревшим запросом с version=0 и сохраняет ссылку происхождения. Повторная активация возможна только с актуальной версией и после проверки применимости источника.

## API

- GET `/api/employees/{id}/production-matrix-overrides?date_from=2026-10-01&date_to=2026-10-31` — сохранённые правки до конца диапазона, их применимость, разреженные интервалы эффективных значений. Необязательный period_key ограничивает период.
- PATCH `/api/employees/{id}/production-matrix-overrides` — создать/изменить правку по устойчивому ключу.
- DELETE `/api/production-matrix-overrides/{id}?version=1` — удалить правку с проверкой версии.

Пример PATCH:

```json
{
  "effective_from": "2026-10-03",
  "scope": "PLAN",
  "field_name": "CONTROL_MODE",
  "control_mode": "OPERATIONAL",
  "assignment_item_id": 123,
  "period_key": "ключ из GET",
  "basis_revision": "версия основания из GET",
  "version": 0
}
```

Для CATEGORY вместо control_mode передаётся category_id; для факта вместо assignment_item_id — fact_id. При создании version=0; при изменении — актуальная version. GET возвращает отдельные интервалы FACT/PLAN с правильной basis_revision для каждого scope. Другие поля запроса запрещены. Неверная категория — 400; неверные поля/режим/форма — 422; устаревшая версия или чужой/неактуальный источник — 409; отсутствующий сотрудник/удаляемая запись — 404.

## Наследование

Используются интервалы сервиса этапа 3А, без второго механизма назначений. Каждое поле выбирает последнее применимое изменение независимо. PLAN ограничен текущим основанием и периодом, следующим изменением того же поля, новым фактом, сменой назначения и убытия/концом периода. Граница месяца сама по себе ничего не обрывает.

FACT относится к одной записи и её дате; эти правки не становятся значениями последующего плана. Для плана от факта нужна отдельная PLAN-правка начиная со следующей даты. Новый факт не наследует старую корректировку, даже на том же объекте.

При удалении правки возвращается предыдущее действующее изменение поля, а если его нет — исходное значение. NO_OBJECT возвращает category_id=null, control_mode=CAMERAL, editable=false; UNKNOWN не подменяется камеральным режимом. Наличие интервала не означает наличие рабочего времени: будущий потребитель должен использовать ЛУВР FINAL.

Запись сериализована тем же advisory lock, что назначения и аннулирование/восстановление билетов; источники проверяются под блокировками. Новые назначения или факты могут изменить применимость уже сохранённой правки; GET показывает это без переписывания исходных данных.
