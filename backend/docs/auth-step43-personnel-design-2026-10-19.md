# Техресурс — шаг 43: проект переводов и временных замещений

Дата: 19.10.2026. Проект C:/Projects/excel-ai-agent-8001.
**Только будущие требования и архитектурные предложения. Таблицы, функции, маршруты, кадровые записи и новые разрешения не созданы.**

## Что имеется сейчас

В рабочем employees есть position_id и crew_id, но нет кадровой категории, истории должностей или замещений. positions содержит текущие name/specialty/work_location/work_schedule/report_description/aos_description/requires_daily_report/planned_count/equipment_description. CALENDAR_SELECT и ряд loaders присоединяют текущую positions через employees.position_id. Следовательно, простой PATCH position_id не обеспечивает требуемую историчность. Текущий app.main.edit_employee безусловно передаёт position_id/crew_id/phone, а repositories.employees.update_employee присваивает их вместе с ФИО; для будущего transfer этот whole-record путь нельзя переиспользовать с непереданными значениями. Требуется явное различение отсутствующего поля и NULL, без изменения текущего кода на этом шаге.

Категория в существующем производственном контуре находится в назначениях, фактах, корректировках и справочнике object_categories; это не доказательство наличия личной кадровой категории. Прежде чем проектировать employee.category_id, надо определить смысл требования. Перевод не должен автоматически менять ни текущий crew_id, ни существующие категории назначений. Если нужна ещё личная квалификационная/кадровая категория, её модель утверждается отдельно.

Поиск в исходниках/документах не подтвердил готовый механизм И.О. с датированными должностями. Отдельная строка ЛУВР для И.О. Руководителя СК принимается как **обязательное требование пользователя этого этапа**, а не как обнаруженная реализация.

## Нормативные требования из запроса

| Требование | Проектный инвариант |
|---|---|
| Должность с установленной даты | Для сотрудника и отчётной даты выбирается ровно одна действующая основная должность либо явный статус неизвестности |
| Сохраняется история | Предыдущие интервалы и версии не теряются; исправления оставляют запись причины/автора/предыдущего значения |
| Сохраняются категория и экипаж | Команда перевода не содержит этих полей и не пишет их таблицы; crew_after=crew_before, категории/назначения неизменны |
| Категория/экипаж отдельно | Отдельные команды Системотехника с самостоятельной проверкой прав и аудитом; не побочный эффект перевода |
| OFFICE_MANAGER только просмотр/экспорт | Нет кадровых write-прав и SQL EXECUTE кадровых команд через читательское соединение |
| Историческая должность | Новый расчёт за дату d использует должность и согласованную версию её реквизитов, действовавшие на d |
| Основная должность при замещении | Не переписывается employee.position_id/основной интервал из-за И.О. |
| Нет двойного времени | Учётная сумма распределений сотрудника за день не превышает единственный исходный рабочий ресурс дня |
| Отдельная строка И.О. Руководителя СК | Видимая самостоятельная строка с устойчивым ключом employee + acting assignment + report role; она не создаёт второго сотрудника |

## Предлагаемая модель данных — имена условные

1. **employee_position_periods**: employee_id, position_id, valid_from, valid_to_exclusive, версия, основание/документ, автор, recorded_at, supersedes/correction reference. Непересечение действующих основных интервалов одного сотрудника, проверка дат, FK. Согласовать, допустимы ли незаполненные интервалы; старые пробелы явно маркировать, а не заполнять догадкой.
2. **position_definition_versions**: версия исторически значимых имени/специальности/графика/места работы/описаний и иных влияющих на отчёт параметров. Ссылка только на текущее positions.id недостаточна: последующее переименование или изменение графика иначе перепишет смысл прошлого. Нужно утвердить состав версионируемых реквизитов и порядок изменения общего справочника.
3. **employee_acting_assignments**: employee_id, acting_position_id/version, начало/конец, основание, режим распределения времени/ссылка на allocation, state/version, автор/аудит. Основные position periods сохраняются. Пересечения замещений либо запрещаются в первой версии, либо допускаются только с доказуемым распределением общего ресурса — это решение ещё не принято.
4. **history of crew/category**, если требуется историчность этих реквизитов: отдельные интервалы/аудит, не часть transfer. Для существующих производственных категорий сохранить их нынешние facts/assignment/override-источники. Личная категория — только после определения её смысла.
5. **report role allocations**: логическое распределение одного исходного employee-day между основной ролью/замещением. Решить, хранить ли только утверждённые намерения распределения и вычислять детерминированно, либо сохранять версионированные утверждённые доли. Не вводить второй календарь или новый независимый источник фактически отработанного времени.

Интервалы предлагаются полуоткрытые [from,to): перевод с 15-го относится новой должности уже 15-го, предыдущее состояние заканчивается перед 15-м. Если UI принимает включающую конечную дату И.О., адаптер переводит её в exclusive-end, с проверкой границ. Правило дат/часового пояса и допустимость внутридневного перевода нужно согласовать; первый проект предполагает кадровую дату, не произвольное время суток.

## Исполнение перевода

1. Проверить авторизацию и тип команды; подготовить исходный DTO без блокирующих чтений на пишущем соединении.
2. В одной контролируемой TX получить общий вход до строк, перепроверить expected history version, основание и доступность должности.
3. Вычислить непротиворечивую новую цепочку интервалов. Будущую запись можно создать сейчас, но текущую должность до effective_date она не заменяет.
4. Записать только историю/версии/аудит перевода. Не применять массовый employee UPDATE из старого профиля с default crew/category=NULL. Наличие других запросов не отменяет блокировки/проверки версии.
5. Сформировать канонические календарные входы для затронутых дат; существующий eligible() использовать через единственный согласованный loader. Зарегистрировать новое намерение, обязательная серверная проверка и SEALED, затем общий COMMIT. Условия включения истории в HMAC описаны ниже.
6. Ответ UI только после успешного COMMIT; повтор по request_id возвращает тот же установленный исход. Сеть на COMMIT — сначала проверить исход, не создавать второй перевод.

Предпочтительно выбирать должность по отчётной дате из истории, без задания, которое ночью переписывает employees.position_id. Если старым потребителям временно нужен current-cache, он не является источником истины; отдельно спроектировать его обновление/валидацию и writer-права. Нельзя включать такой worker незаметно или забыть его в порядке D.

## Исторические отчёты

Один `position_as_of(employee,date)`/канонический адаптер исторических входов используется календарём, ЛУВР, матрицей, daily validation, ВОУ и экспортом. Это проект интерфейса, не новый SQL-календарь. Существующие календарные расчёты и временные роли не дублируются альтернативной упрощённой формулой.

При переводе в середине месяца дни до/после даты относятся к своим ролям/версиям; группировка может дать две строки сотрудника по разным периодам. Устойчивый row-key не должен быть только ФИО. Дневное время при этом остаётся одним, а итог по сотруднику не удваивается. Политика, какие текущие отчётные формы разделяют строки, требует отдельного согласования шаблонов.

Ранее опубликованный архив ВОУ остаётся неизменяемым snapshot. Повторно сформированный исторический отчёт использует известную историю на соответствующие даты и фиксирует версию расчёта/входов. Ретроисправление требует явного процесса переиздания, а не подмены старого UUID/файла. Снимки заголовка luvr_months не являются историей должности каждого сотрудника.

Начальную историю нельзя достоверно восстановить из единственного текущего position_id. Перед переносом нужны подтверждённые даты/основания; для неизвестного прошлого — явный статус и диагностическое сообщение. Автоматически считать текущую должность действующей с даты приёма или «всегда» запрещается проектом.

## Временное замещение и ЛУВР

Общий календарь один раз даёт доступный рабочий ресурс employee-day. И.О. распределяет этот ресурс между отчётными ролями, а не добавляет второй ресурс. Для нормализованных долей можно хранить целые единицы: FULL=100, HALF=50; суммы распределений не превосходят исходное значение. Это не формула оплаты и не замена графика. Если форма считает часы, требуется согласованное отображение единиц в часы, а не произвольное умножение на 8/12.

Для полного замещения возможен вариант: И.О.-строка получает весь рабочий ресурс, основная строка на эти даты не добавляет отработанное время. Для частичного — только явно согласованные доли/периоды. Автоматическое 50/50 или две строки FULL в один день не предлагаются. Нерабочие коды/болезнь/отпуск сохраняют исходные правила; замещение само по себе не создаёт рабочий день.

Отдельная строка **«И.О. Руководителя СК»** сохраняется в ЛУВР. Основная должность остаётся в кадровой истории. Уточнить оформление основной строки на период И.О. (0/прочерк/нерабочий код) и печатный шаблон; визуальное дублирование сведений не должно означать двойной числовой итог. Общее число сотрудников считать по employee_id отдельно от количества строк должностей/И.О.; плановые показатели и штатные единицы также не смешивать с отработанными долями.

Пример только для объяснения инварианта: основной работник имеет ресурс FULL=100; при утверждённом полном замещении основная учётная доля 0, И.О. 100, итог 100. При HALF=50 сумма распределений максимум 50. Доли, подписи и правила отчётного вывода должны быть утверждены, пример не вводит их автоматически.

## Влияние на ДК/HMAC

Будущие history/acting/definition/allocation-источники не входят в нынешние девять таблиц отпечатка. Новая запись истории без обновления loader/контекста/серверных триггеров была бы обходом контроля. Перед кадровой реализацией требуется новая версия протокола и полный перечень зависимостей, obligation на source-пути, nonce-инвалидация, общий gate, повтор отрицательных/конкурентных проверок.

При проверке ДК за дату d основной position-loader обязан учитывать перевод на d. **Как именно И.О. влияет на пригодность ДК (основная или выполняемая временная должность, график, доля), запросом не определено.** Нельзя автоматически выбрать основную должность и объявить проблему решённой. Это бизнес-вопрос до внедрения замещений. Единственный eligible() должен получать согласованные канонические данные; новая независимая SQL-копия правил не предлагается.

Перевод, созданный заранее, должен сразу учитываться в проверках ДК на соответствующие будущие даты. Ночной DML-worker для наступления effective_date не нужен, если чтение действительно датированное. Это свойство будущего проекта, не подтверждённая возможность нынешнего CALENDAR_SELECT.
