## Состав месяца

`luvr_months` хранит факт формирования, даже когда все строки вручную убраны. `luvr_month_employees` хранит только идентификатор связи, год, месяц, employee_id и время создания. UNIQUE(year, month, employee_id) исключает дубли, FK сотрудника использует RESTRICT.

Первое явное формирование включает всех неархивных сотрудников, у которых дата увольнения отсутствует либо не раньше первого дня месяца. Дополнительного скрытого фильтра по должности нет: сотрудники без настроенного графика тоже видны, с пустым автоматическим календарём. Это позволяет исправить справочник, не теряя сотрудника из состава.

GET ничего не создаёт. Повторное формирование не меняет существующий состав, не добавляет новых сотрудников и не возвращает вручную убранных. Архивирование и увольнение после формирования не удаляют строку. Уволенный внутри месяца включается; в следующий первоначально формируемый месяц — нет.

Ручное добавление выбирает существующего сотрудника, включая архивного, и создаёт только связь с месяцем. Повторное добавление идемпотентно. «Убрать из месяца» требует подтверждения и удаляет только эту связь. Сотрудник, назначения, Журнал, билеты, перемещения, болезни и корректировки сохраняются. Физический DELETE сотрудника по-прежнему запрещён.

Формирование атомарно: вставка заголовка с ON CONFLICT определяет единственный первый запрос. Добавление/удаление блокируют строку заголовка FOR UPDATE. Уникальность дополнительно обеспечена PostgreSQL. Получение состава и всех исходных фактов выполняется одним SELECT, в одном снимке данных. Сортировка — полное ФИО после схлопывания пробелов, приведения регистра и ё/е; ID используется только при одинаковых ключах сортировки.

## Расчёт

Каждая строка вызывает `calculate_employee_month` этапа 4. Второго алгоритма календарных дней нет.

- OBJECT + SHIFT и OFFICE + SHIFT: прежние ARRIVAL/DEPARTURE, RAIL travel, SELF, переходы между месяцами и UNKNOWN.
- OFFICE + FIVE_TWO: реальные понедельник–пятница FULL, суббота–воскресенье EMPTY; перемещения не влияют. Производственные праздники на этом этапе не вводились.
- FIVE_TWO без корректного OFFICE: режим CONFIGURATION_ERROR, диагностическое предупреждение, автоматическое значение пустое.
- Болезнь оставляет итог пустым, не изменяя историю движения. Причина видна в деталях.
- Корректировки используют прежний POST day-overrides (upsert), отмена — DELETE конкретного override. Допустимы все семь значений, включая работу в выходной и ручной DISMISSED, который не меняет dismissal_date.
- Приоритет этапа 4 сохранён: увольнение задаёт постоянную границу; на дату увольнения DISMISSED, после EMPTY. Болезнь подавляет ручное значение; противоречащая корректировка сохраняется и сопровождается предупреждением.
- DOWNTIME автоматически не выводится из перемещений.

Итоги рассчитываются из final_code на каждом GET: FULL=1, HALF=0.5; TRAVEL, OFF_SHIFT, DOWNTIME считаются раздельно. EMPTY и DISMISSED не добавляют рабочее время. Болезнь не входит в эти показатели; sick_days_count — отдельный информационный счётчик. manual_changes_count считает существующие корректировки, в том числе подавленные болезнью/увольнением. Итоги в БД не хранятся.

Метаданные — актуальные ФИО, должность, НРС, специальность, место и график из employees/positions. Изменение справочника влияет и на отображение/расчёт исторического месяца; временное версионирование не добавлено.

## API

Все ответы используют существующую оболочку `{status:"ok", item:...}` и Pydantic schemas. Маршруты присутствуют в `/openapi.json` и `/docs`.

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/luvr/month?year=2026&month=10` | Признак формирования, состав, дни, метаданные и итоги |
| POST | `/api/luvr/month/form` | Первичное формирование |
| POST | `/api/luvr/month/employees` | Добавить существующего сотрудника |
| DELETE | `/api/luvr/month/employees/{employee_id}?year=2026&month=10` | Убрать только связь |

Тело формирования: `{"year":2026,"month":10}`.

Тело добавления: `{"year":2026,"month":10,"employee_id":25}`.

Ответ изменения состава: `{"status":"ok","item":{"formed":true}}`.

GET несформированного месяца: `{"status":"ok","item":{"year":2026,"month":10,"days_in_month":31,"formed":false,"employees":[]}}`.

Сформированный месяц содержит `employees[]` с `employee_id`, `full_name`, `position_name`, `nrs_number`, `specialty`, `work_location`, `work_schedule`, `is_archived`, `dismissal_date`, `mode`, `days[]`, `totals`. Дни сохраняют контракт этапа 4: auto/final code и display, причины, предупреждения, состояние, болезнь, override. Итоги: `work_days_total`, `travel_days_total`, `off_shift_days_total`, `downtime_days_total`, `manual_changes_count`, `sick_days_count`.

Добавление до формирования — HTTP 409; неизвестный employee — 404; неверный год/месяц — 422. Изменение дня использует существующие `/api/employees/{id}/luvr/day-overrides`.

## SQL миграции 009

```sql
-- A header preserves the distinction between an empty and an unformed month.
CREATE TABLE IF NOT EXISTS luvr_months (
    year INTEGER NOT NULL CHECK (year BETWEEN 1 AND 9999),
    month INTEGER NOT NULL CHECK (month BETWEEN 1 AND 12),
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (year, month)
);
CREATE TABLE IF NOT EXISTS luvr_month_employees (
    id BIGSERIAL PRIMARY KEY,
    year INTEGER NOT NULL,
    month INTEGER NOT NULL,
    employee_id BIGINT NOT NULL REFERENCES employees(id) ON DELETE RESTRICT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (year, month) REFERENCES luvr_months(year, month) ON DELETE RESTRICT,
    UNIQUE (year, month, employee_id)
);
CREATE INDEX IF NOT EXISTS ix_luvr_month_employees_employee ON luvr_month_employees(employee_id);
```
