## Реализованный протокол

В отдельной временной копии используется прежний NOLOGIN-владелец закрытой dk_service, его ключ и минимальные права на ДК. Дополнительно создаются закрытая tx_state и функции touch(), tx_context(), tx_snapshot(), register_intent(text[],bytea), finish(). Кандидату доступны только два новых служебных входа tx_snapshot()/register_intent(); прямые UPDATE/DELETE ДК не выдавались. EXECUTE старых snapshot()/prune() в этой копии у кандидата отозван. PUBLIC EXECUTE служебных функций закрыт.

1. BEFORE STATEMENT на восьми календарных источниках берёт общий транзакционный advisory lock до изменения кандидатом. Создаёт/обновляет закрытое состояние по top-level txid, выдаёт случайный nonce и аннулирует прежнее намерение. При SEALED запрос отвергается.
2. prepare() получает согласованный снимок и вычисляет список только существующим eligible(). Во время вычисления принудительно установлен доверенный search_path с pg_temp последним; прежний путь восстанавливается после вычисления. Ключ остаётся в доверенной памяти и закрытой таблице, не передаётся атакующим SQL-запросам.
3. HMAC связывает dk37, имя временной БД, PID/txid, отпечаток девяти таблиц, nonce и канонический список. register_intent проверяет доказательство и записывает контекст/список в закрытую tx_state. В этот момент ДК не удаляются.
4. DEFERRABLE INITIALLY DEFERRED constraint trigger на закрытом состоянии делает проверку обязательной на сервере. Прямой COMMIT не обходит её. Отсутствующее/устаревшее намерение вызывает исключение. На этой стадии подпись уже проверена при регистрации, список хранится в недоступной клиенту таблице, а полный контекст повторно сравнивается с текущим.
5. При применении атомарно устанавливается SEALED и удаляется только заверенный список. Повторные отложенные события видят SEALED и ничего не удаляют повторно. Собственное изменение таблицы ДК не сверяется ошибочно с исходным отпечатком после удаления.
6. Даже если SET CONSTRAINTS вызывает применение раньше COMMIT, последующие изменения календарных источников кандидатом отвергаются. GUC dirty и самодельный dk_service.sealed не управляют закрытым состоянием.

В испытанной модели после успешного COMMIT автоматическая очистка не должна удалить ДК, для которого eligible() истинен на окончательном сериализованном состоянии источников. Проверенные случаи подтверждают инвариант; это не формальное доказательство всех возможных расширений схемы и кода.

## Отрицательные испытания нового протокола

20 тестов нового набора:
- Регистрация не удаляет ДК; корректный COMMIT применяет очистку.
- Прямой SQL COMMIT без намерения отвергается даже после dirty=0; источники и ДК откатываются.
- Восстановление FULL после регистрации делает намерение устаревшим и отклоняет COMMIT.
- Раннее применение через SET CONSTRAINTS, затем восстановление FULL: отказ и откат без потери пригодного ДК.
- SAVEPOINT после очистки, повторные FULL/TRAVEL/HALF и ROLLBACK TO не снимают SEALED.
- ROLLBACK TO точки до очистки возвращает ДК и служебное состояние; новое корректное намерение позволяет завершить HALF без потери отметки.
- Вложенные transaction()/RELEASE SAVEPOINT не удаляют ДК преждевременно — проверено обычным psycopg и тестовым наследником MatrixConnection.
- SET CONSTRAINTS ALL IMMEDIATE без корректного намерения отклоняется; с корректным намерением раннее применение и последующий COMMIT успешны.
- Именованные IMMEDIATE/DEFERRED и клиентские GUC не позволяют изменить источник после SEALED.
- Прямые UPDATE/DELETE ДК, SELECT/UPDATE/DELETE служебного журнала, внутренние функции, старый prune(), отключение триггеров и CREATE TEMP TABLE отклоняются PostgreSQL.
- Поддельная подпись и старое доказательство из откатанной ветви SAVEPOINT отвергаются; фиксированный контекст подписывающего расчёта не подменяется изменённым search_path.
- Конкурирующий кандидатный писатель получает lock_timeout до изменения источника; откат не оставляет частичных результатов.
- Ошибка после уже применённой очистки откатывает источник, ДК и SEALED. Следующая транзакция работает.
- Изменение сотрудника/архивного состояния, обработка билета, HALF/TRAVEL и отсутствие проходят через SignedIntentConnection.
- На одинаковом изменении полностью совпадают список ДК, результат calculate_month (включая календарные/ЛУВР-поля матрицы) и чистая подготовка ВОУ prepare_data после исходного reconcile и после нового применения.

Сравнение выполняется на тестовом январе 2030. Реальный октябрь не пересчитывался, новый COM/XLSM/PDF не формировался, печать и рабочий архив не проверялись/не менялись.

Обе атаки шага 35 сохраняются в отдельной старой контрольной БД: успешный тест reproduces_* там означает подтверждение прежней уязвимости. В новой копии тесты требуют отказа/отката либо сохранения пригодных ДК. Прежний prune не является альтернативным входом к данным новой копии: базы разные, его EXECUTE в новой копии закрыт. ## Влияние и оставшиеся ограничения

Календарные правила не копируются и не меняются. Меняется транзакционная политика: после раннего применения изменение любого из восьми источников запрещено; до применения промежуточные изменения допустимы, но требуют свежего намерения. Устаревание определяется консервативно даже после UPDATE, не изменившего бизнес-значения. SET CONSTRAINTS IMMEDIATE до регистрации может привести к раннему отказу, а не автоматическому подписанию. Это сознательный fail-closed и отличие от старой системы.

Права кандидатной роли и её произвольный SQL проверены в конфигурации без PUBLIC TEMP/CREATE. Исключения для доверенной инфраструктуры реализованы через точное session_user кандидата: fixture-роль не обязана подписывать setup/cleanup. Поэтому прототип не доказывает безопасность для произвольных других пишущих ролей, суперпользователя или владельца объектов. Для рабочего проекта надо отдельно определить все роли-писатели, ручные ДК и административное обслуживание, запретить недоверенные обходные роли и проверить их сериализацию. Текущая рабочая суперроль не подпадает под это доказательство.

Кража ключа/контроль доверенного Python, неполный перечень зависимостей календаря, новые SECURITY DEFINER обходы и ослабление ACL остаются за границей испытанной модели. Блокер рабочих PUBLIC ACL шага 32 не устранён. READ COMMITTED — единственная поддерживаемая изоляция. Нагрузочная стоимость полного хеширования/общего lock ещё не измерена.

Закрытые строки tx_state остаются после COMMIT в временной БД; production-retention/очистка не реализованы. Нужен отдельный проект безопасной очистки старых состояний и оценка роста таблицы, без доступа кандидата к журналу. Хранение/ротация реального ключа, рабочая миграция, подключение протокола к защищённому приложению и полноценная HTTP-цепочка на новой БД не внедрялись. Файловые операции PostgreSQL не откатывает: атомарность БД не распространяется автоматически на публикацию файлов.

Известного обхода нового протокола кандидатом в проверенных сценариях не выявлено. Это ограниченный результат испытаний, не утверждение о полном пентесте или готовности к рабочему включению.
