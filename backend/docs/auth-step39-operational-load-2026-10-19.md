## Когда запускается ДК

Фактические восемь matrix_dk_calendar_change включены (tgenabled=O). Это BEFORE INSERT OR UPDATE OR DELETE FOR EACH STATEMENT без UPDATE OF/WHEN/сравнения OLD/NEW. Функция берёт pg_advisory_xact_lock(20261017,29) и выставляет локальный dirty=1. Lock удерживается до окончания транзакции. Правка телефона, ФИО, экипажа, описания должности, комментария истории и объекта билета тоже запускает путь. Даже DML с нулём изменённых строк/INSERT ON CONFLICT DO NOTHING вызывает statement-триггер. Нулевое число ДК не означает отсутствие lock и SQL обслуживания.

MatrixConnection.commit вызывает _reconcile_dk перед COMMIT; transaction() — при выходе из контекста, в том числе вложенного. Поэтому в билетной цепочке sync(connection=conn) через production_assignments.save может вызвать обслуживание перед RELEASE SAVEPOINT, ещё до формирования окончательного ответа. После очистки dirty сбрасывается: следующий выход без новых source DML не делает повторный полный reconcile. Если источники снова изменены, обслуживание возможно снова в той же внешней транзакции. Новый прототип намеренно меняет этот порядок: вложенное действие только регистрирует намерение, фактическое удаление отложено.

Календарный алгоритм eligible использует должность/архив/увольнение/лимиты и истории/подтверждённые поездки. Состав месяца ЛУВР не является условием автоматического удаления. Не следует смешивать дневные employee_luvr_day_overrides с production_matrix_overrides: вторая таблица не входит в восемь источников ДК.

## Как читать количество SQL

Числа ниже — явные клиентские SQL вызовы успешной бизнес-ветви до обслуживания, без BEGIN/COMMIT, авторизации, конструирования соединения, внутренних FK/триггерных SQL. Это статический подсчёт и формулы ветвлений, не замер request roundtrips. Количество .execute в AST само по себе не равно числу запросов при циклах/вызовах помощников.

Для действующего старого пути одна проверка dirty добавляет 1 SELECT при активной транзакции. Для dirty-TX полный добавочный путь K = 5 + N + A + D клиентских SQL: N существующих ДК проверяются первым календарным SELECT, A из них доходят до запроса отсутствий, D удаляются. Пять — чтение dirty, installed, lock, список ДК, сброс dirty. При пустом ДК K=5. Два PERFORM внутри statement-триггера идут на сервере, не являются двумя дополнительными клиентскими roundtrip. Каждая source DML вызывает marker, но несколько DML внутри одной TX не обязательно означают несколько полных обслуживаний.

Для билетов: T=4 для _ticket(lock=True) при действующей identity (проверка наличия + два advisory SELECT + SELECT FOR UPDATE). V=Q(_view): количество зависит от статуса, совпадения сотрудника, объекта, отсутствий, identity и прочего; это SELECT-помощники, не постоянное число. S=Q(sync), зависит от существующих назначений/строк, иногда равно нулю; H=проверки reference/prepare, F=проверки ПО/категории. Полный числовой итог сложной HTTP-цепочки без её исполнения не установлен; формулы явно сохраняют неизвестные части. Точные трассы в изолированной среде потребуют следующего разрешённого этапа. Здесь не подставляются вымышленные константы.

## Пакеты, параллелизм и риски

Билетный upload на текущем main допускает до 50 файлов/запрос с ограничением размера; подготовленный payload_guard разрешает только один файл. Это не ограничивает страницы одного PDF: parse_rail_document проходит все страницы, явного отдельного лимита числа страниц не найдено. process_document сохраняет поддержанные страницы последовательно, по одной TX на страницу. Разбор PDF выполняется до сохранения страниц; парсер не должен удерживать DK-lock этой транзакции. Повторная загрузка дубликата всё равно выполняет INSERT ON CONFLICT и marker, даже когда новой строки нет.

Контроллер билетов последовательно отправляет свои batches и имеет uploading для своей страницы. Это не глобальный mutex: разные вкладки/запросы/скрипты могут работать параллельно. pending ограничивает действие лишь на одном ticket id, другие билеты могут обрабатываться одновременно. Promise.all при загрузке справочников и истории — преимущественно чтение, не доказательство 5–10 календарных писателей. Синхронные endpoints и run_in_threadpool для upload допускают перекрытие запросов; точное число одновременно работающих пользователей не установлено и не выводится из одного процесса Uvicorn.

### Потенциальный цикл блокировок, не воспроизведённый экспериментом

Фактические определения из БД сохранены в read_only.json. validate_construction_reference безусловно берёт identity-lock (20261013,24) до проверки, что у нового билета object/entity пусты. matrix_dk_calendar_change — BEFORE STATEMENT; identity_reference_guard — BEFORE ROW.

Возможное расписание:
1. T1 — загрузка нового билета: BEFORE STATEMENT получает DK(20261017,29), затем row-trigger ждёт identity(20261013,24).
2. T2 — PATCH объекта другого билета: set_ticket_object заранее получает (20261007,1601) и identity(24), затем его UPDATE rail_tickets ждёт DK(29).
3. T1 ждёт T2, T2 ждёт T1. PostgreSQL может выбрать транзакцию-жертву deadlock.

Обе операции разрешены E в подготовленной политике. Это подтверждённая кодом/каталогом инверсия порядка и потенциальный цикл, но факт реального deadlock этим аудитом не установлен. Никаких конкурентных запросов не запускалось. Стресс шага 38 менял только employees.full_name и не покрывал этот смешанный маршрут/identity-trigger, поэтому нулевой deadlocks там не исключает этот риск.

Дополнительный возможный цикл: crew-memberships держит FOR UPDATE сотрудников до DK-lock; другой UPDATE employees уже держит DK через BEFORE STATEMENT и ждёт те же строки. Эта bulk-операция DENY защищённым ролям, но есть в текущем незащищённом main. Предварительные FOR SHARE сотрудника в confirm и FK-проверки также требуют отдельного анализа общего порядка. Риски не исправлялись.

PostgreSQL рекомендует согласованный порядок получения нескольких блокировок; statement/row-триггеры и advisory lock выполняются внутри транзакции. Источники: [Explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html), [Trigger behavior](https://www.postgresql.org/docs/18/trigger-definition.html).

Полного журнала всех запросов/HTTP-действий с пользователем, числом TX и длительностью lock в проекте не найдено; auth Security Events не заменяют аудит всех производственных запросов, auth_users сейчас пуст.

Поэтому ни интенсивность λ (TX/сек), ни C одновременных календарных TX, ни их длительности из этого среза не вычисляются. Количество строк не используется как статистика реальных пользовательских операций.

## Предварительные требования — предложения, не утверждённые SLA

1. Инвариант сохранности пригодного ДК, атомарность, запрет ручного DELETE кандидату и серверный отказ устаревшему намерению сохраняются независимо от нагрузки; скорость не оправдывает ослабление.
2. Для обычной одиночной интерактивной записи предложить бюджет полного HTTP-ответа p95 ≤1 с, p99 ≤2 с, исключая PDF/COM. Это предположение для согласования; сейчас полный HTTP-путь не измерен.
3. Сохранить обсуждавшиеся ориентиры добавочных затрат ДК p95 ≤250 мс, p99 ≤1 с, но согласовать метод измерения: разности непарных квантилей недостаточно для приёмки индивидуальной добавки. Цель ожидания lock p95 ≤500 мс оценивать на согласованном Cpeak, а не автоматически на пяти людях.
4. Cnormal/Cpeak, λ, B и максимальное время транзакции пока НЕ определены. Для предварительного диагностического базиса использовать уже измеренный C=1; это предположение о серии, не оценка реальных пользователей. C=5/10 сохранять как стресс-границы до подтверждения их эксплуатационной необходимости.
5. Пакетный срок считать отдельно от времени одной TX: для страниц — примерно сумма парсинга, отдельных TX и очередей; для атомарного импорта — полный срок одной TX. Числовой batch-SLA без размера/частоты/атомарности не устанавливать.
6. Не считать успехом частичную фиксацию и не повторять слепо весь пакет после неопределённого COMMIT; поведение ошибок/дедупликации и сообщений пользователю должно быть согласовано. Политика deadlock/timeout также требует решения, автоматический retry не добавлялся.
