# Удаление ЖД-события вместе с билетом

Реализовано 03.10.2026. Миграций нет. Рабочая БД тестами не изменялась.

## Операция

В истории сотрудника для RAIL доступна кнопка «Удалить», без кнопки редактирования. Открывается отдельное подтверждение «Удалить ЖД-событие?» с перечислением удаляемых данных и кнопками «Отмена» / «Удалить». Отмена не отправляет запрос.

Расширен существующий endpoint:

```text
DELETE /api/employees/{employee_id}/luvr/movements/{item_id}?delete_ticket=true
```

Пример ответа:

```json
{"status":"ok","id":42,"deleted":true,"ticket_id":17}
```

Параметр явно разрешает совместное удаление и передаётся UI только после подтверждения. Без него прежняя защита связанного с билетом события сохранена; PATCH также остаётся запрещённым. Обычный DELETE SELF не изменён.

Repository блокирует конкретный ticket, затем конкретное движение, проверяет employee_id, RAIL, CONFIRMED и связь по movement_id. Порядок блокировок соответствует подтверждению билета. Сначала удаляется ticket, затем movement — строго в одной транзакции. FK из rail_tickets указывает на employee_movements с RESTRICT, изменения FK/CASCADE не потребовались.

При ошибке обе операции откатываются. FK/RESTRICT-конфликт возвращает HTTP 409 с понятным сообщением, транзакция остаётся пригодной для следующих запросов. Чужой employee/movement или повторное удаление — 404. RAIL без корректного источника — 409, без удаления наугад.

## Границы удаления

Удаляются только выбранный movement и связанная запись rail_ticket. Сопоставление по имени файла, source_sha256 или всем страницам PDF не используется. Проверка фактических FK рабочей БД показала единственную соответствующую связь: rail_tickets.movement_id → employee_movements.id. Отдельных таблиц служебных данных, ссылающихся на rail_tickets, нет.

Физический PDF не удаляется. Другие страницы/билеты того же файла, сотрудники, SELF/прочие movements, болезни, overrides, назначения и Журнал сохраняются.

При удалении ticket освобождается его уникальный file_hash (для многостраничного PDF — существующий fingerprint конкретного билета/страницы). Прежняя загрузка PDF создаёт запись заново; оставшиеся билеты по-прежнему возвращаются дублями. Парсер и механизм fingerprint не менялись.

## Обновление интерфейса

Успешный ответ обновляет историю в карточке сотрудника. Событие `luvr-rail-deleted` удаляет только соответствующую карточку билета из загруженного списка, сбрасывает устаревшие календарные данные и перечитывает месячный и индивидуальный календарь. Продолжительность и индикация пересчитываются существующим backend вместе с месяцем.

Для удалённых ticket ID действует локальная защита от запоздавших ответов: старый upload/refresh не возвращает удалённую карточку. Новый ticket ID после повторной загрузки принимается нормально. Другие билеты из того же PDF остаются в интерфейсе.

## Проверки

- **303 backend-теста прошли**, включая все прежние и 7 новых.
- **156 frontend-тестов прошли**, без пропусков, включая общие модальные окна Chrome/CDP.
- Удаление пары ticket/movement; сохранение запрета PATCH и удаления без явного флага.
- Прежний DELETE SELF.
- Реальный fixture PDF с двумя билетами: удаление первого не изменяет второй ticket и его movement; повторный upload создаёт только удалённую запись, второй остаётся дублем; повторное подтверждение не создаёт дополнительные movements.
- Искусственный FK RESTRICT на movement блокирует второй DELETE: уже выполненный DELETE ticket откатывается, обе записи сохранены, последующие запросы и повторная попытка после устранения препятствия работают.
- Снимки всех остальных строк в изолированной схеме до/после равны; проверены чужой employee_id, отсутствующий источник и повторное удаление.
- Индивидуальный календарь, месячные дни/итоги, duration и индикация пересчитываются после удаления и обычной повторной загрузки/подтверждения.
- Настоящий Chrome: RAIL без редактирования, подтверждение двумя кнопками, отмена без DELETE, совместное удаление, исчезновение истории и карточки билета, сохранность других событий, запросы обновления обоих календарей, повторная загрузка и подтверждение с новыми ticket_id/movement_id. Ошибок JavaScript нет. Изолированный сценарий удалил ticket 2 / movement 4 и создал replacement ticket 3 / movement 5; это не ID рабочей БД.
- Рабочий сервер: HTTP 200 для `/`, `/docs`, `/openapi.json`, сотрудников, истории и месячного ЛУВР. OpenAPI содержит delete_ticket.
- `git diff --check` — ошибок нет.

SHA256 относительно начала задачи подтверждает неизменность rail parser, Salym/exact matching, fingerprint/duplicate protection backend, рекурсивной загрузки, calculation layer, Word parser, Journal и aliases. Изменение rail_tickets.js ограничено синхронизацией списка после удаления, разбор билетов не менялся.

## Проверка конкретной ошибочной записи

Пользователю запрошены ФИО, дата/время и исходный PDF либо ID movement/ticket. На момент отчёта эти сведения не предоставлены. Конкретная ошибочная запись рабочей БД не определена и не удалялась. Полный цикл удаления/повторного парсинга проверен на изолированных данных; для рабочего случая нужно однозначно указать запись и источник.

Доработка готова; Excel и другие этапы не выполнялись.
