Вкладка «Объекты строительства»: иерархия и безопасный перенос подобъектов.

До изменения: плоский список основных объектов с поиском только по названию основного объекта, созданием, переименованием и удалением. Отдельные подпанели «Категории» и «ПО». Категория и ПО назначаются через существующее назначение сотрудника; собственных полей категории/ПО у подобъекта не появилось.

После изменения: расширен существующий список, сохранены его кнопки работы с основными объектами и подпанели. Новый вспомогательный JS-файл обслуживает только иерархию справочника и его форму подобъекта.

Пример (тестовые данные):

```text
▼ Обустройство куста №55
  Подобъектов: 2 · Активных: 2
    ├─ Коридор коммуникаций  [Активен]   [Редактировать]
    └─ Площадка             [Активен]   [Редактировать]
  [+ Добавить подобъект] [Редактировать объект] [Удалить объект]

▼ Обустройство куста №56
  Подобъектов: 2 · Активных: 1
    ├─ Подъезд переименован [Активен]   [Редактировать]
    └─ Старый подъезд       [Неактивен] [Редактировать]
```

По умолчанию показываются активные подобъекты, счётчик учитывает активные. Фильтр «Все» показывает также неактивные и оба счётчика. Фильтры «С подобъектами»/«Без подобъектов» учитывают выбранную активность. Основные объекты без статуса не получают искусственного статуса активности.

Поиск работает по названиям основных объектов и подобъектов. Совпадение по подобъекту показывает родителя, раскрывает его и показывает найденные дочерние записи с учётом фильтра активности. Поиск выполняется в загруженном справочнике, отдельный дублирующий search API не добавлен. Сортировки основных объектов: А–Я, Я–А, ID по возрастанию, количество подходящих под фильтр подобъектов по убыванию. Дочерние записи всегда А–Я внутри своего родителя. Раскрытие сохраняется в пределах страницы при обновлениях списка.

Добавление открывается из известного родителя; повторно выбирать его не нужно. Используется `POST /api/subobjects`. Переименование и активация/деактивация используют существующий `PATCH /api/subobjects/{id}`. Нормализованные дубли, включая неактивные, запрещены прежним индексом; UI показывает «Такой подобъект уже существует у этого объекта.».

Для смены родителя добавлены только две операции в существующий router:

- `POST /api/subobjects/{id}/move/check` — предварительная проверка без изменения записей. Вход: `object_id`, необязательные `name`, `is_active`. Ответ: старый/новый родитель, количество связанных фактов, число фактов без подходящего назначения на нового родителя, `requires_confirmation`, `confirmation_token`.
- `PATCH /api/subobjects/{id}/move` — атомарное применение тех же изменений. Для использованного подобъекта требуется `confirmation_token` из проверки и отдельное нажатие «Перенести» в форме.

Транзакция блокирует подобъект, проверяет нового родителя и нормализованное имя, блокирует запись в таблицу фактов на время проверки/переноса и проверяет проекцию UNIQUE на нового родителя. Читатели журнала могут продолжать работать. Затем обновляет `construction_subobjects.object_id` и `daily_control_results.object_id` всех фактов с данным `subobject_id`. Имя и статус из формы применяются в той же транзакции. Другие поля фактов не меняются. При конфликте — 409 и откат; при иной ошибке записи транзакция также откатывается полностью.

Токен связывает подтверждение с текущим родителем, содержимым связанных фактов и параметрами операции. Если после предварительного просмотра появились новые факты или изменились проверяемые данные, требуется повторная проверка и подтверждение. Отмена ничего не записывает. Для неиспользованного подобъекта подтверждение истории не требуется.

Отсутствие назначения на нового родителя выводится предупреждением и не блокирует перенос. `employee_assignments` не создаются, не перепривязываются и не удаляются. Подобъект после деактивации доступен через фильтр «Все»/«Неактивные»; история журнала продолжает показывать его имя.

DELETE подобъекта отсутствовал и не добавлен. Прямое удаление используемого подобъекта защищено существующим FK. Удаление основного объекта дополнительно возвращает понятную ошибку при наличии подобъектов или истории.

Сценарий ручной проверки:

1. Открыть «Объекты строительства», раскрыть объект.
2. Нажать «Добавить подобъект». Проверить выбранного родителя, ввести уникальное название, добавить.
3. Убедиться в расположении под родителем и обновлении счётчика; переименовать.
4. Перезагрузить страницу, открыть вкладку и найти подобъект по новому названию. Проверить раскрытие родителя.
5. В редактировании выбрать другого родителя. Для неиспользованной записи сохранить; проверить нового родителя.
6. Для используемой записи нажать «Сохранить» и проверить окно подтверждения: старый/новый родитель, число фактов, предупреждение об отсутствующих назначениях.
7. Сначала нажать «Отмена»: родитель и история должны остаться прежними.
8. Повторить перенос и нажать «Перенести». Открыть Журнал: все связанные факты должны относиться к новому родителю, остальные поля остаться прежними.
9. Деактивировать подобъект. В фильтре «Все»/«Неактивные» он должен быть виден со статусом «Неактивен»; история должна остаться доступной.
10. Проверить сортировки, фильтры наличия подобъектов, создание/редактирование основного объекта, подпанели категорий и ПО.

Миграции и изменения структуры БД не потребовались. Структура факта прежняя: Дата + Инженер + Объект/Подобъект + ПО + Субподрядчик (если есть) + Категория.
