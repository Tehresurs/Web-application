## Среда и модель атаки

Собственный временный PostgreSQL, БД auth_stage3_1945fd3c002742d6b6e864e50807a679, ограниченная кандидатная роль, без прямых UPDATE/DELETE ДК. Фикстуры создавались отдельной ограниченной инфраструктурной ролью. Рабочие привилегированные реквизиты не передавались тестовому приложению. Рабочее соединение supervisor использовалось только для READ ONLY проверки отпечатков.

Атакующие SQL-запросы не знают ключ. В сценариях корректной подписи доверенный prototype.prepare() сам вычисляет непригодность через существующий eligible() и выдаёт настоящее доказательство. Это модель исполнения произвольного SQL до/после доверенной очистки в том же соединении, а не доказательство возможности получить подпись одним автономным SQL-клиентом. Без вызова доверенного подписывающего компонента подделка подписи по-прежнему отвергается.

## Реально воспроизведено

1. В одной транзакции FULL меняется на TRAVEL. prepare() законно подписывает удаление, prune() удаляет отметку. Затем SQL восстанавливает FULL. SignedConnection перед COMMIT повторяет служебную очистку. После COMMIT существующий eligible() возвращает True, но отметки нет; три остальных тестовых ДК сохранены. Повторная очистка не восстанавливает удалённые строки.
2. То же нарушение воспроизведено с SAVEPOINT после удаления, повторными FULL/TRAVEL/HALF, ROLLBACK TO SAVEPOINT и окончательным восстановлением FULL перед COMMIT. Откат к точке после удаления оставляет удаление в транзакции.

Подпись здесь не подделана: она удостоверяет промежуточное состояние. Отпечаток в prune() не удостоверяет окончательное состояние при COMMIT. Один только штатный порядок вызовов backend недостаточен для заявленной более сильной модели угроз.

## Доказанные отказы в испытанной конфигурации

- search_path=pg_catalog, public,pg_catalog и pg_temp,pg_catalog: prepare() завершается UndefinedTable, удаления не происходит; транзакция откатывается.
- CREATE TEMP TABLE employees, CREATE TABLE public.employees, CREATE TABLE в бизнес-схеме и CREATE SCHEMA: серверный InsufficientPrivilege. Эффективные TEMP и CREATE закрыты, включая права PUBLIC. Подмена таблиц с этими ACL не воспроизведена.
- Восстановление источника ДО prune(): прежняя подпись отвергается, ДК остаются после отката.
- SAVEPOINT ДО изменения и очистки: ROLLBACK TO возвращает и источник, и удалённые ДК; COMMIT сохраняет исходное состояние.
- Предыдущие сценарии поддельной подписи, подмены списка, повторного использования в другом соединении/транзакции, прямого DELETE/UPDATE и чтения ключа также прошли.

## Потенциальные риски, не выдаваемые за воспроизведённые

Рабочий PUBLIC сохраняет TEMP/другие права по шагу 32. Комбинация TEMP и неквалифицированных запросов eligible() требует отдельного регрессионного стенда с намеренно ослабленными ACL. В этом прогоне ACL кандидата не ослаблялись, поэтому утверждения об экспериментально доказанном обходе через временные таблицы нет. Результат закрытого стенда нельзя переносить на рабочий кластер с иными ACL.

## Исправление и граница разрешённого этапа

Исправление прототипа не вносилось. Простое повторное хеширование при prune(), повторный reconcile перед COMMIT или фиксация search_path не устраняют воспроизведённое восстановление после удаления. Запрет всех изменений источников после prune() отклонит часть последовательностей, которые прежняя логика допускает; это новая транзакционная политика. Автоматическое восстановление ДК, отложенное до COMMIT применение или хранение закрытых подписанных намерений требуют отдельного механизма, проверки окончательного контекста и SAVEPOINT, без доверия к изменяемому клиентом GUC. Их нельзя объявить минимальным безопасным исправлением без дополнительных испытаний.

Для согласования: (а) строгий запрет изменений источников после очистки с защищённым серверным учётом состояния; (б) проект отложенного применения подписанного решения с обязательной финальной валидацией и отказом COMMIT при устаревании; (в) независимая проверка тем же единственным алгоритмом в доверенной среде БД. Варианты (а)/(б) могут отклонять ранее допустимые транзакции, (в) требует архитектурной адаптации. Прямые UPDATE/DELETE ДК приложению не предлагаются. Ни один вариант не внедрён.
