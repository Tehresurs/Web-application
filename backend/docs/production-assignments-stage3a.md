## Хранение

`production_assignment_changes` содержит датированное изменение полного набора, ссылку происхождения на заезд, билет, отпечатки основания, версию и снимки исправленных версий. `production_assignment_items` содержит объекты набора, ссылки на действующие справочники, исходную категорию и режим.

Для OBJECTS требуется хотя бы одна строка, для NO_OBJECT — ни одной. Отложенные constraint triggers проверяют конечное состояние транзакции. Проверка подобъекта выполняется также триггером БД. Уникальность набора учитывает NULL; смена change_id у существующей строки запрещена.

Ссылка на движение намеренно не является физическим FK: действующий механизм аннулирования удаляет движение, а затем может восстановить тот же ID. Удаление движения не удаляет историю назначений. Ссылка на employee_assignments также является только происхождением: удаление прежнего закрепления не изменяет датированный набор. Остальные ссылки на справочники и билеты защищены FK.

PATCH — исправление полного события с обязательной version, не переход на новую дату по обычному сценарию. Предыдущее событие вместе со строками сохраняется в correction_history. Неизменённые строки сохраняют ID; заменённые получают новые ID. Перенос события в другой период запрещён. Новая рабочая дата/набор вводятся POST.

## API

- GET `/api/employees/{id}/production-assignments?date_from=2026-10-01&date_to=2026-10-31`
- POST `/api/employees/{id}/production-assignments`
- PATCH `/api/production-assignments/{id}`

POST пример:

```json
{
  "effective_from": "2026-10-01",
  "period_kind": "ARRIVAL",
  "arrival_movement_ref": 123,
  "source_kind": "MANUAL",
  "assignment_state": "OBJECTS",
  "items": [{
    "object_id": 1,
    "po_id": 1,
    "initial_category_id": 1,
    "initial_control_mode": "INSPECTION"
  }]
}
```

Для NO_OBJECT передаётся пустой items. Для источника TICKET требуется source_ticket_id подтверждённого билета выбранного заезда; набор должен включать объект билета. Дополнительные объекты допустимы. Билет не изменяется. Для офиса 5/2 поддержан EXPLICIT с явными period_start/period_end без фиктивного движения. Пересекающиеся разные явные периоды запрещены. PATCH передаёт полный аналогичный набор полей плюс version.

GET возвращает `item.history` — сохранённую историю с применимостью; `item.periods` — разреженные интервалы, включая основание и видимую часть выбранного диапазона; `item.facts` — исходные факты выбранного диапазона; `item.warnings` — неоднозначные движения/факты без известного периода. История содержит также неприменимые и находящиеся вне диапазона события, чтобы они не терялись.

## Правила интервалов

Последний полный набор действует до следующего набора или факта, убытия, следующего заезда либо явного конца периода/увольнения. Убытие ограничивает период включительно своей датой: доступное время этого дня необходимо брать из ЛУВР FINAL. Следующий заезд всегда является отдельным основанием. Месяц просмотра не обрывает период.

Все факты сотрудника одной даты собраны вместе и заменяют план на этой дате. Они являются основанием дальнейшего плана, без копирования в новые таблицы. Более поздний ручной набор может сменить назначение. На совпадающей дате факт приоритетнее ручного набора. Факты вне известного периода возвращаются с предупреждением, а не открывают вымышленный период.

NO_OBJECT означает явное отсутствие объекта и вычисляемый CAMERAL. Неизвестное назначение имеет UNKNOWN и не подменяется камеральным. Сами интервалы не доказывают наличие рабочего времени: болезнь, выходной и остальные ограничения берутся будущим потребителем из существующего ЛУВР.

При аннулировании/восстановлении билета применимость пересчитывается чтением без hooks в билетах. Изменение сотрудника/типа/времени исходного заезда или объекта источника делает старое основание неприменимым. Повторные события в один день не разрешаются угадыванием. Следующий заезд без убытия является новой границей и не наследует старый набор.

## Ограничения этапа

Нет интерфейса, автоматической записи назначений из формы билета, расчёта долей времени, таблицы overrides и наследования пользовательских правок режимов. API уже позволяет явно создать назначение от подтверждённого билета. Категория и режим пока являются исходными независимыми полями назначения. Неопределённые ПО/категория/режим сохраняются как NULL, без автоматического выбора.

Нет новых записей в существующих таблицах и автоматической конвертации старых закреплений. Исторические периоды без достоверного заезда не восстанавливаются предположениями. Нет нескольких внутридневных наборов одного периода: модель дневная.

Для офиса 5/2 используется только EXPLICIT: старые движения не создают параллельный период. FK на используемые билеты/справочники защищают историю от физического удаления; аннулирование и восстановление билета работают без удаления назначения.
