## 3. Calculation layer и read-only

```text
GET календаря / дня
  → один SELECT employee + position + вся история movements
    + конкретные подтверждённые rail_tickets + sickness + overrides
  → чистый CalendarTimeline
  → auto_code / final_code / основания / предупреждения
```

Repository получает согласованный снимок в одном SQL-запросе, включая сведения о графике из должности. Не выполняет INSERT/UPDATE/DELETE, блокировок строк или создания производных событий. Связь билета берётся строго через `movement_id`, `employee_id` и `status='CONFIRMED'`; неподтверждённые билеты в расчёт не попадают.

Месячная функция использует тот же метод расчёта дня, что и `calculate_employee_day`. Расчёт не зависит от текущего времени и не использует AI. Хранение float 0.5 не вводилось: возвращаются существующие коды FULL/HALF/TRAVEL/OFF_SHIFT/DOWNTIME/DISMISSED/EMPTY.

## 4–5. Начальное состояние и UNKNOWN

Вся история сортируется по местному `event_datetime`, затем по ID для стабильного порядка диагностических данных. События не ограничены месяцем. Последнее событие до даты устанавливает ON_SHIFT после ARRIVAL или OFF_SHIFT после DEPARTURE.

Если более раннего события нет, состояние UNKNOWN, автоматический код EMPTY, отображение пустое. Первое событие не переносит состояние назад во времени. При совпадающих timestamps противоположных событий состояние остаётся UNKNOWN до следующего однозначного события: порядок ID не используется для угадывания бизнес-состояния.

## 6–10. Правила значений

| Событие | Время | Код | Отображение |
|---|---|---|---|
| ARRIVAL | раньше 08:00 | FULL | 1 |
| ARRIVAL | с 08:00 до 13:00, не включая 13:00 | HALF | 0,5 |
| ARRIVAL | с 13:00 | TRAVEL | Д |
| DEPARTURE | раньше 13:00 | TRAVEL | Д |
| DEPARTURE | с 13:00 до 20:00, не включая 20:00 | HALF | 0,5 |
| DEPARTURE | с 20:00 | FULL | 1 |

Для дня события используется `event_datetime`, без UTC-конвертации. Последующие полные дни ON_SHIFT получают FULL, OFF_SHIFT — OFF_SHIFT/МВ. Максимальные сроки не создают автоматические заезды или выезды. Открытая последовательность допустима и продолжается до следующего подтверждённого события.

Для RAIL ARRIVAL из конкретного подтверждённого билета берутся `departure_datetime` и `arrival_datetime`. Все календарные даты от отправления до дня перед прибытием включительно — TRAVEL/Д. День прибытия получает значение по времени ARRIVAL. При поездке в тот же день отдельный день дороги не добавляется.

TRAVEL имеет приоритет над OFF_SHIFT и может быть известен даже до первого movement, если подтверждённый билет явно задаёт эти даты. Пересечение поездки с ON_SHIFT, другой поездкой или другим событием этого дня требует проверки, а не молчаливого выбора.

RAIL DEPARTURE не добавляет дорожные дни после выезда: со следующей даты продолжается МВ. SELF использует только время события и не получает предварительных дорожных дней.

RAIL ARRIVAL без связанного подтверждённого билета рассчитывает день самого известного события, но не выдумывает даты поездки; возвращается `RAIL_SOURCE_MISSING`. Противоречие даты/маршрута билета событию даёт `RAIL_SOURCE_CONFLICT` и требует проверки.

## 11. Границы месяцев

Сентябрьские события задают начальное состояние октября. Прибытие в ноябре может задать дни дороги в конце октября: будущие подтверждённые билеты также входят во входные данные. Нет отдельной несовместимой логики для границ месяцев. Учтены длины месяцев и високосный февраль.

## 12–14. Болезнь, override, увольнение

Автоматическое значение движения сохраняется в `auto_code`. При override итоговое значение берётся из `override.value`, а `manually_changed=true`. Возвращаются ID, код и комментарий корректировки. Удаление override штатным DELETE возвращает вычисляемый итог. Перерасчёт после изменения движения не удаляет корректировку.

Болезнь включает обе границы периода; NULL date_to означает открытый период. Итог — EMPTY, `is_sick=true`, текст «Болеет» в ячейку не записывается. Auto остаётся доступным, движение состояния не меняется. При совпадении с override он сохраняется, но перекрывается болезнью; возвращается `SICK_OVERRIDE_CONFLICT`.

`dismissal_date` даёт auto DISMISSED в день увольнения и EMPTY после него, в том числе в последующих месяцах. Сотрудник и история сохраняются.

**Принятый приоритет для неуточнённого пересечения:** увольнение выше болезни и override на эту дату и после неё. Этот вариант был предложен в вопросе; отдельного ответа не поступило, поэтому реализован как явно зафиксированное допущение, а не как дополнительно согласованное правило. Ручная запись не удаляется, возвращается `DISMISSAL_OVERRIDE_CONFLICT`; совпадение увольнения с болезнью также диагностируется. До увольнения болезнь выше override, override выше автоматического значения.

## 15. Архив и графики

Архивный сотрудник рассчитывается по той же истории, доступен в выборе с отметкой «архив». Архивирование не меняет прошлое. OBJECT+SHIFT и OFFICE+SHIFT рассчитываются одинаково. FIVE_TWO возвращает режим `FIVE_TWO_NOT_CALCULATED_AT_THIS_STAGE` без заполнения месяца по movements. Неуказанный график — `UNKNOWN_WORK_SCHEDULE`, без предполагаемого SHIFT. Известные болезнь, увольнение и явные корректировки остаются доступны как самостоятельные факты.

## 16–17. Противоречия и несколько событий

- ARRIVAL после ARRIVAL или DEPARTURE после DEPARTURE: `MOVEMENT_SEQUENCE_WARNING`; безопасное состояние берётся из последнего события. История не исправляется.
- Два или более события на одну дату: auto EMPTY, `calculation_status=NEEDS_REVIEW`, `MULTIPLE_MOVEMENTS_DAY`; все ID событий доступны. Утренний заезд и вечерний выезд не складываются в выдуманную долю дня.
- После такого дня последнее по времени событие определяет дальнейшее состояние, если оно однозначно.
- Противоположные события в один timestamp: `SIMULTANEOUS_MOVEMENTS`, неизвестное дальнейшее состояние до следующего однозначного события.
- Конфликт поездки с другими фактами: `RAIL_TRAVEL_CONFLICT`.

Пользователь может ввести ручное значение для дня, но предупреждение остаётся видимым. Болезнь и увольнение имеют описанный выше приоритет.

## 18. API

```http
GET /api/employees/25/luvr/calendar?year=2026&month=10
GET /api/employees/25/luvr/calendar/day?target=2026-10-20
```

Ответы в стиле проекта: HTTP 200, `{ "status": "ok", "item": ... }`. Месяц содержит employee_id, full_name, year/month, work_location/work_schedule, is_archived, dismissal_date, mode и days. Несуществующий сотрудник — 404; неверная дата, год или месяц — 422. Schemas присутствуют в Swagger.

Пример дня после ручной корректировки (иллюстрация контракта):

```json
{
  "date": "2026-10-15",
  "auto_code": "FULL",
  "auto_display": "1",
  "final_code": "DOWNTIME",
  "final_display": "П",
  "manually_changed": true,
  "is_sick": false,
  "movement_ids": [17],
  "warnings": [],
  "state": "ON_SHIFT",
  "calculation_status": "CALCULATED",
  "source_type": "STATE",
  "final_source_type": "OVERRIDE",
  "override_id": 4,
  "override_code": "DOWNTIME",
  "override_comment": "Согласовано"
}
```

При редактировании используются существующие POST `/api/employees/{id}/luvr/day-overrides` с work_date/value/comment и DELETE `/api/employees/{id}/luvr/day-overrides/{override_id}`. Новый способ записи корректировок не создан.

## 19. Интерфейс

Вкладка **«Календарь ЛУВР»**: сотрудник (включая архив), месяц и «Обновить расчёт». Таблица показывает дату, автоматическое и итоговое значение, признак ручного изменения, основания, предупреждения и ID событий. Это технический просмотр расчёта, не утверждённый месячный состав и не Excel.

«Редактировать» открывает форму для семи существующих значений и комментария. «Вернуть автоматическое значение» удаляет только корректировку. Смена сотрудника/месяца сбрасывает старый редактор, поздние ответы предыдущего запроса не заменяют новый календарь. Двойное сохранение блокируется. Названия и комментарии вставляются через textContent, без интерпретации HTML.

После изменения истории или подтверждения нового билета достаточно следующего GET/кнопки обновления; отдельная синхронизация и копирование movements не нужны.
