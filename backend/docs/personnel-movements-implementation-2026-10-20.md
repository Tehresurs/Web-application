## Что реализовано

Доработан существующий employee_transfers.js, а не демонстрационная страница. Кнопка карточки открывает окно «Перемещение сотрудников» с существующими стилями ui-input/ui-button/ui-table и dialog, выбором сотрудника из /api/employees, автоматической основной должностью только для чтения и тремя режимами. Должности загружаются из /api/positions по существующим ID. Объекты/подобъекты выбираются через ConstructionChoices с каноническими entity_id, без синтеза legacy-ID.

Форма меняет поля по типу операции, проверяет обязательные значения, показывает этап подтверждения, блокирует повторное нажатие во время запроса и не сохраняет данные по кнопке отмены. Загрузка справочников и датированных сведений завершается до подтверждения. После успеха обновляются карточка и история. Текущая должность не редактируется вручную. Отдельный выбор исходной должности появляется только при неизвестной истории накануне даты перевода.

### Постоянный перевод

На дату вступления начинает действовать новая основная должность. Прежнее наблюдение и все события сохраняются. Датированная проекция работает без планировщика, меняющего employees.position_id в будущем. Сотрудник и его ID остаются прежними; полная строка employees, экипаж, движения, билеты, прежние назначения и факты не изменяются кадровой командой.

Исходная должность берётся на день ДО даты перевода. Для неизвестного периода пользователь выбирает её из того же справочника: записываются source_position_id, source_on и признак явного указания. Дата первоначального назначения не выдумывается; более ранний неизвестный период остаётся неизвестным. Последующие переводы не удаляются. Несовместимость с записанной исходной должностью следующего перевода отклоняется; это проверяется также при исправлении и отмене.

Исходные график и место работы сохраняются в кадровой проекции отдельно от параметров новой должности. В действующем справочнике «Инженер СК ТА» (ID 16) имеет requires_daily_report=false. Для нового перевода в ТА из кадрового состояния с обязательным инженерным отчётом сохраняется прежняя обязанность, как требует ТЗ. Справочник и существующие сотрудники ТА этим исключением не переписываются.

### Временное И.О.

Основная должность сохраняется. Отдельный журнал personnel_acting_events хранит назначения и ревизии сроков/завершения/отмены. Даты обязательны, последний день включён; пересечения одного сотрудника отклоняются. По окончании периода назначение перестаёт действовать при чтении, без изменения сотрудника фоновым заданием. На карточке действующее И.О. показывается отдельно от основной должности.

Для Руководителя СК используется строка «И.О. Руководителя СК» рядом с ФИО. Обязанность отчёта определяется датированной кадровой политикой, без общего освобождения любого И.О. от отчётов. Уже существующую фактическую отчётность в затрагиваемом интервале команда не переосмысляет: даёт безопасный отказ для отдельного разбора. Если факт поступил ПОСЛЕ оформления И.О., он остаётся FACT, сохраняется в матрице и не становится обязательным инженерным отчётом периода И.О.

Исправление срока и отмена сохраняют аудит и используют прежнюю выделенную возможность review. SYSTEM_TECHNICIAN не получает общих прав отмены; OFFICE_MANAGER не получает запись. Завершённое с планом назначение нельзя скрыто переоткрыть или отменить, оставив несогласованный план: такой случай требует отдельной проверки.

### Завершение И.О. и инженерный план

В форме выбирается назначение, последний день И.О. и один или несколько объектов. Система показывает существующие применимые периоды планирования. Возвращение и новое закрепление начинаются на следующий день. Для вахты нужен действующий реальный заезд; для офисного 5/2 применяются существующие явные границы периода. Недостающий заезд, противоречие периода или конфликт существующего назначения не обходятся созданием фиктивного движения.

Использован именно production_assignments.save(..., connection=conn), без отдельной системы планирования. План и событие END коммитятся одной транзакцией. Неверный объект, ошибочная дата или устаревшая версия откатывают оба изменения. Повтор request_id с тем же payload возвращает прежний результат без второго плана; другой payload отказывается выполняться.

Старые объекты другим инженерам не передаются. После истечения И.О. без подтверждённого возвращения старый план не возобновляется скрыто: требуется новый подтверждённый план; матрица показывает отсутствие надлежащего закрепления. Добровольно поступившие факты при этом не удаляются. Реквизиты ПО/категории/режима, которых нет в выборе объекта, не выдумываются; сохраняется штатная диагностика неполного назначения.

## Транзакции и полномочия

Именованные кадровые операции получают D(20261017,29) → T(20261007,1601) → I(20261013,24). Перевод/назначение затем блокируют общую строку версии. Завершение в репозитории сначала под теми же D/T/I вызывает существующий writer плана (его FK/locking SELECT сохраняются), затем кадровая команда блокирует версию. Все новые операции сериализованы D; это не доказательство общего порядка для старых произвольных SQL/импорта/администраторов.

Проверяются текущая сессия AuthService, CSRF и прежние права. После ожидания D права повторно проверяются до записи. Новых прикладных ролей/реальных пользователей/паролей нет. Числовые actor/session_id — доверенный серверный контекст после HTTP-проверки, а не криптографическое доказательство для владельца SQL-соединения. Новый минимальный runtime/полный закрытый контур шага 45 не внедрялся.

HMAC/nonce/signed intent/SEALED старых прототипов не ослаблялись и не переписывались; SHA256 четырёх прежних установщиков/прототипов совпали с контрольным снимком шага 45. **Расширение подписанного контекста на кадровые таблицы ещё не реализовано.** Декларативный перечень будущих зависимостей содержит также personnel_acting_events, но сам по себе не является подписью. Рабочие enabled/dk_context_verified/date_readers_verified не выставлялись. В тестах они заданы фикстурой только для проверки кадрового ядра.
