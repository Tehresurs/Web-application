## Актуальное исправление: автоматическое направление по Салыму

Ручной выбор направления отменён по уточнённому требованию пользователя. Это заменяет прежнее описание подсказки направления и обязательного ручного выбора ниже и в основном отчёте этапа 3.

- Салым → Сургут или Тюмень: **DEPARTURE**, время отправления.
- Сургут или Тюмень → Салым: **ARRIVAL**, время прибытия.
- Без Салыма: **NOT_LUVR_ROUTE**, без employee matching и movement.
- Неполные факты маршрута или Салым → Салым: **Требует проверки**, без matching и movement; ручного обхода блокировки нет.

UI показывает направление текстом и предлагает только явное подтверждение готового билета. Upload по-прежнему не создаёт событие. Исходные данные билета, регистронезависимое точное сравнение станций, нормализация ФИО нового сотрудника, архив, SHA-256 и рекурсивная загрузка сохранены.

Repository вычисляет направление из маршрута при выдаче неподтверждённого билета и заново под блокировкой перед Confirm. У новых билетов оно сохраняется сразу. Старая вручную выбранная величина у незавершённого билета не может подменить направление: при подтверждении фиксируется вычисленное значение. Уже подтверждённая история не переписывается. Старый PATCH `/direction` помечен deprecated: совпадающее направление возвращает текущую карточку без записи, противоположное отклоняется HTTP 409. Интерфейс этот маршрут не вызывает.

## Рекурсивная загрузка

«Выбрать папку» использует существующий `webkitdirectory multiple`: браузер собирает файлы во всех вложенных папках, независимо от глубины. В multipart отправляется только `file.name`, без `webkitRelativePath` и абсолютного клиентского пути.

Для Drag & Drop папок добавлен обход браузерных `FileSystemEntry`: `webkitGetAsEntry`, `createReader`, последовательные вызовы `readEntries` до пустого результата. Учтено, что браузер возвращает содержимое каталога несколькими порциями. Обход выполняется итеративно, без ограничения глубины в коде и без рекурсивного стека JavaScript. Ошибка чтения отдельного элемента показывается отдельно, остальные элементы продолжают обрабатываться. Если API каталогов недоступен, работает прежний Drag & Drop файлов; папку можно выбрать кнопкой.

Все способы используют прежний `/api/rail-tickets/upload`. Выбор более 50 файлов больше не отклоняется целиком: frontend разбивает набор на запросы не более 50 файлов и 50 МиБ каждый. Лимит одного файла остаётся 10 МиБ. Ошибка запроса одной части не прекращает загрузку следующих частей. Сам обход папок выполняется браузером, сервер не читает клиентские каталоги.

## Фильтрация перед matching

Обновлённый pipeline:

```text
Рекурсивный набор файлов / отдельные файлы
  → тип и структура поддерживаемого купона РЖД
  → UNSUPPORTED для постороннего файла: конец его обработки
  → parser → факты маршрута
  → точное наличие станции Салым
  → NOT_LUVR_ROUTE при отсутствии: конец его обработки
  → точное сопоставление сотрудника
  → направление → предпросмотр → явное подтверждение → RAIL
```

Неподдерживаемый тип, PDF другого макета, скан без нужного текстового слоя, зашифрованный/многостраничный документ показываются как **«Не является поддерживаемым билетом РЖД»** (`UNSUPPORTED`). Такие файлы не сохраняются в `rail_tickets`. Повреждённый PDF, пустой файл, превышение размера или отсутствие обязательных фактов в распознанном купоне остаются `PARSE_ERROR` и не останавливают пакет.

Корректный разобранный билет без Салыма получает **«Не относится к ЛУВР — маршрут без станции Салым»** (`NOT_LUVR_ROUTE`), без ошибок парсинга. Его факты и SHA-256 сохраняются для защиты от повторной загрузки; технический статус хранения остаётся `PARSED`, а отдельный `processing_status` рассчитывается по маршруту. Это позволяет обойтись без изменения CHECK существующей таблицы и применять фильтр также к ранее загруженным незавершённым билетам.

Для такого билета repository не вызывает поиск сотрудника. В карточке нет matching, создания сотрудника, выбора направления и Confirm. Проверка повторяется в endpoints выбора направления и подтверждения: даже прямой API-запрос с заранее записанным направлением возвращает HTTP 409, movement не появляется. Следовательно, такой новый билет не добавляет фактов для будущего расчёта ЛУВР. Уже подтверждённую историю дополнение не переписывает; расчёт календаря не добавлен.

## Салым и направление

Название станции сравнивается после trim, схлопывания повторных пробелов и приведения регистра. Совпадение строгое: `Салым`, `САЛЫМ`, ` Салым ` допустимы; `Салымский` и `Салым 2` — другие станции. Similarity, fuzzy и aliases не применяются. В предоставленных реальных билетах станция указана как `Салым`, без кода или регионального суффикса; дополнительные варианты не выдумывались.

В ответ добавлены `is_luvr_route`, `direction_candidate`, `notice` и два новых значения `processing_status`. По двум предоставленным образцам:

- Салым → Сургут: кандидат **DEPARTURE / Выезд**.
- Тюмень → Салым: кандидат **ARRIVAL / Заезд**.
- Салым с обеих сторон: кандидат отсутствует, нужен ручной выбор.

Подсказка показана в карточке. Окончательный выбор направления остаётся явным; затем требуется отдельное подтверждение. Никаких скрытых movement не создаётся. Правило выбора времени остаётся прежним: прибытие для ARRIVAL, отправление для DEPARTURE.

## Статистика

Сводка последнего выбранного набора показывает количество полученных файлов, разобранных билетов РЖД, файлов со станцией Салым и без неё, ненайденных сотрудников, требующих проверки, готовых к подтверждению, дубликатов, ошибок и посторонних файлов. Дубликаты считаются по исходным файлам набора, даже если карточки объединены по ticket ID. Статусы сводки обновляются после действий с карточками. Это пересекающиеся категории, их не следует суммировать.

Билет без Салыма не увеличивает количество ошибок парсинга. Счётчик «Билетов РЖД (разобрано)» относится к успешно извлечённым обязательным фактам, а не к любому PDF с расширением .pdf.
