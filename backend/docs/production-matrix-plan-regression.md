# Проверка будущего плана и объединение строк

08.10.2026.

## Формирование плана

Выявлен дефект в `app/services/production_matrix.py`: ветка автоматического CAMERAL для `requires_daily_report=false` выполнялась до чтения действующего объектного назначения. Факт оставался FACT на своей дате, но следующий день ошибочно становился камеральным, хотя `project()` уже возвращал полный набор объектов как основу плана.

Минимальное исправление: приоритет факта → действующего объектного назначения (в том числе от предыдущего факта) → явного NO_OBJECT → автоматического CAMERAL при false и отсутствии действующего назначения. Пересекающиеся периоды не маскируются автоматическим CAMERAL. При true неизвестное назначение сохраняет предупреждение.

Используются прежние `project()`, `resolve()`, CalendarTimeline и реальные структуры PostgreSQL. Переписывания расчёта периодов не потребовалось.

Проверены:

1. FACT на исходной дате и PLAN со следующей доступной даты.
2. Полный набор из нескольких подтверждённых объектов, доли 0,33/0,33/0,34.
3. Полная замена набора новым фактом и явным датированным назначением.
4. Остановка после убытия и отсутствие наследования старого набора после нового заезда: при true предупреждение, при false допустимый автоматический CAMERAL.
5. Продолжение набора из фактов 29 октября в ноябре в незавершённом периоде.
6. Независимые корректировки категории/режима, прекращение их действия при смене основания, отдельные версии и источники каждой даты.
7. Прекращение применимости плана после аннулирования билета и восстановление после возврата того же подтверждённого билета. Исходные факты не меняются.
8. Доли по существующему FINAL ЛУВР, включая половину дня; ежедневные строки плана в БД не создаются.

Факт вне достоверного производственного периода по-прежнему видим как конфликт: неизвестный период не подменяется вымышленным. Для офисной объектной работы сохраняется существующее требование явного периода назначения.

## Объединение строк

Причина повторов: прежний ключ строки включал PLAN/FACT, ID факта/назначения и период. Один объект распадался на отдельные строки при смене источника.

Новый ключ отображения: сотрудник + вид строки + объект + подобъект + ПО + субподрядчик. Категория и режим остаются значениями конкретной даты; интерфейс уже умеет отображать «Меняется по датам». В каждой ячейке сохранены исходные FACT/PLAN, ID факта/назначения, период, версия корректировки и доля. Общая строка может иметь `source=MIXED`, но источник каждой ячейки однозначен.

При нескольких записях с одинаковыми объектными реквизитами на одну дату сохраняются отдельные стабильные строки: ни один факт и его цель редактирования не перезаписываются и не объединяются в необратимую сумму. Группировка выполняется после расчёта долей, поэтому на округление и проверку времени не влияет. Итог строки суммирует её сохранённые ячейки.

На одном текущем ответе рабочего октября: 68 сотрудников, 348 строк при прежнем ключе источника против 135 сгруппированных строк; 72 строки содержат и FACT, и PLAN. Это сравнение способов отображения одного набора ячеек, а не сравнение разных исторических выгрузок.
