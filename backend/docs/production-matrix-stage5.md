## Интерфейс и API

Месяц переключается без перезагрузки страницы. Строка сотрудника раскрывается непосредственно в таблице; вложенные строки показывают ПО, объект/подобъект, категорию, режим, субподрядчика и дневные доли. Факт выделен сплошной линией и «Ф», план — пунктирной линией и «Пл». Панель справа показывает все производственные строки выбранного дня, состояние ЛУВР, доли, предупреждения и конфликты. Подтверждённый конфликтующий факт остаётся видимым.

- `GET /api/production-matrix?year=...&month=...` — весь результат, календарь, строки, проверки и итоги.
- `GET /api/object-categories` — действующий справочник категорий.
- `PATCH /api/employees/{id}/production-matrix-overrides` — категория либо режим выбранной ячейки, её дата, область, идентификаторы источника/периода и версия конкретного поля.

После PATCH результат повторно читается из backend. Изменение PLAN наследуется сервером, FACT относится к конкретному факту. Если значения строки различаются по датам, выводится «Меняется по датам»: редактирование всегда привязано к выбранной дате. Разрешены только CATEGORY и INSPECTION/OPERATIONAL. Камеральные строки не редактируются. При ошибке сохранения отображается сообщение и обновляются данные/версии; автоматической повторной записи нет.

Frontend не рассчитывает время, доли или итоги. При проверке JSON выявлено отсутствие общих дневных итогов. Минимальное расширение существующего ответа — `day_totals`, суммирующий уже рассчитанные проверки сотрудников и выбирающий наиболее серьёзный статус. Алгоритмы ЛУВР и распределения долей не изменены.

## Уточнение: автоматический камеральный контроль

Последующая проверка исправила приоритет относительно действующего объектного плана: CAMERAL теперь является резервным правилом при отсутствии назначения. Актуальное поведение и регрессионные проверки описаны в `production-matrix-plan-regression.md`; описание ниже фиксирует первоначальную реализацию этапа 5.

На дату с подтверждёнными объектными фактами используются эти факты независимо от признака должности. Факт на нерабочий день сохраняется как конфликт.

На дату без подтверждённого факта, если `requires_daily_report` строго равен `false` и по ЛУВР доступно рабочее время, оно автоматически распределяется в CAMERAL. Ручное событие NO_OBJECT не требуется. Это правило применяется и вместо рассчитанного объектного плана для такой должности. Источник автоматического решения обозначен `basis_kind=POSITION_RULE`; в деталях показана причина. Никакие события или факты в БД не записываются.

При `true` неизвестное назначение по-прежнему вызывает предупреждение. Уже существующее явное NO_OBJECT остаётся достоверным основанием камеральной работы. Неизвестный признак должности не приравнивается к false.

Камеральное время выводится отдельной строкой и участвует в сравнении с ЛУВР вместе с объектным временем. Нерабочие дни автоматически камеральными не становятся.
