# Восстановление аннулированного билета

07.10.2026. На экране билетов для ANNULLED показывается «Восстановить билет», для действующего — «Аннулировать билет». Новый POST `/api/rail-tickets/{id}/restore` возвращает состояние до аннулирования, а не назначает CONFIRMED всем билетам.

Миграция 016 добавляет nullable `rail_tickets.annul_snapshot`. Перед аннулированием в одной транзакции сохраняются прежний статус и полная запись связанного движения. Билет, хеш PDF, разобранные данные и назначенный объект остаются в БД. Прежний механизм исключения движения из расчёта сохранён; снимок позволяет вернуть исходное движение с тем же ID и датами. Повторные операции идемпотентны, параллельные аннулирования/восстановления сериализованы транзакционной блокировкой. Конфликты восстановления откатываются и возвращают 409.

PARSED/PARSE_ERROR/REJECTED восстанавливаются без создания движения. Для PARSED точное сопоставление и состояние проверки, как и прежде, вычисляются из текущих данных. Подтверждённый билет восстанавливает исходную связь с сотрудником и движением без повторного matching. Восстановление не меняет архивное состояние сотрудника.

Расчёт ЛУВР не переписан: восстановленные данные читаются существующим расчётным слоем. Событие frontend `luvr-ticket-state-changed` обновляет уже открытые месячный ЛУВР и подробный календарь. Физическое удаление билетов в этот сценарий не добавлялось; контроль дублей продолжает использовать прежний хеш.

Миграция применена к рабочей БД. Найден один ранее аннулированный билет без снимка. Его прежний статус старым механизмом не сохранялся: восстановление возвращает понятный 409 и не угадывает состояние. Автоматический backfill не выполнялся.

Изменения: repository/API/JS билетов; два существующих обработчика обновления UI ЛУВР; версии ресурсов в `processing.html`. Созданы миграция/runner 016, backend/frontend и браузерные тесты. Тестовые схемы дополнены существующими миграциями 014/015 и новой 016; конкурентный fixture дополнен полями, которые уже требует экран билетов. Проверка наличия таблиц отсутствий использует текущий search_path вместо public, чтобы изолированные схемы не зависели от рабочей БД.

Проверены: цикл подтверждённого билета, равенство календаря до аннулирования и после восстановления, возврат статусов проверки, повторные циклы, повторная загрузка PDF, откат после ошибки, запрет изменения аннулированного билета, идемпотентность миграции и конкурентное восстановление. Браузерный сценарий выполнен на изолированной схеме: кнопки, исходные ID, календарь, события обновления, отсутствие JS-ошибок. Рабочие билеты этими тестами не изменялись.

Итоговые полные наборы: backend — 381 тест прошёл; frontend — 178 прошли, без пропусков, включая браузерный modal test через Chrome/CDP. Первый backend-прогон выявил устаревшие тестовые схемы без полей миграции 014 и без таблицы должностей в конкурентном fixture; после приведения fixtures к используемой схеме повторный полный прогон прошёл.
