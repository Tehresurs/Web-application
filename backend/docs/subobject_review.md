# Этап 5 — подобъекты в проверке отчёта

Word-парсер и исходный `object_name` не меняются. Назначения остаются
`employee_id + object_id + po_id + category_id`; используется родительский объект.

## Matching

1. Exact основного объекта.
2. Object alias.
3. Exact активного подобъекта.
4. Subobject alias.
5. Прежний fuzzy-порог 0.75 для объектов и активных подобъектов.

Несколько одинаковых подобъектов у разных родителей требуют выбора, если нет
явного alias. Кандидаты имеют `entity_kind`, `score` (0–1), `similarity` для
совместимости. Подобъект содержит `subobject_id/name` и `object_id/name` родителя.
Found-статус сохраняет совместимость с проверкой назначений; происхождение
отражает `object_match_source`: `subobject_exact` или `subobject_alias`.

Примеры (условные ID):

- Exact: «Подъезд к кусту скважин №55» → подобъект 12, родитель 5
  «Обустройство куста скважин №55». Метка «ПОДОБЪЕКТ НАЙДЕН».
- Alias: «Подезд к кусту №55» → subobject alias с target_id=12 → тот же родитель 5.
  Метка «ИЗВЕСТНОЕ СООТВЕТСТВИЕ ПОДОБЪЕКТА».
- Fuzzy: «Подезд к кусту скважин №55» → кандидат типа `subobject`, ID 12,
  название подобъекта, название родителя и процент похожести. Требуется выбор.

«Запомнить соответствие» создаёт `object` alias для основного объекта и
`subobject` alias для подобъекта. Исходное значение отправляется без изменения.
Создание основной записи или подобъекта само по себе alias не создаёт.

## Ручная проверка

1. Подготовить Word со строкой «Подъезд к кусту скважин №55» и распознанными
   датой, инженером и ПО. В базе должен существовать родитель
   «Обустройство куста скважин №55» с назначением этого инженера на нужное ПО.
   Самого подобъекта и alias для исходного написания пока быть не должно.
2. Обработать отчёт, открыть «Результат проверки».
3. В строке объекта со статусом ПОХОЖЕЕ/НОВОЕ нажать «Добавить как подобъект».
4. Встроенная форма показывает исходное название. При необходимости исправить
   его. Найти родителя поиском и явно выбрать в списке.
5. Нажать «Сохранить подобъект». POST `/api/subobjects` создаёт запись.
6. Проверка показывает отдельно «Объект: Обустройство куста скважин №55»
   и «Подобъект: Подъезд к кусту скважин №55».
7. Проверить назначение: оно ищется по родителю, а не по ID подобъекта.
8. Нажать «Сохранить результат». При отсутствии конфликта прежнего UNIQUE
   сохраняется факт, например:

```json
{
  "report_date": "2026-09-24",
  "employee_id": 1,
  "object_id": 5,
  "subobject_id": 12,
  "po_id": 3,
  "category_id": 2,
  "source_file": "report.docx"
}
```

Это пример формата, не запись, внесённая в рабочую БД тестами.
Обычный объект сохраняет `subobject_id = NULL`. Перед записью сервер проверяет
существование, активность и принадлежность подобъекта выбранному родителю.
Явный `subobject_id: null` очищает автоматически найденный подобъект.

Журнал возвращает название подобъекта и отдельный `subobjects_count`.
`objects_count` по-прежнему считает разные основные `object_id`.
В UI журнала добавлена колонка детализации без нового фильтра или вкладки.

INFO-события: SUBOBJECT_EXACT_MATCH, SUBOBJECT_ALIAS_MATCH,
SUBOBJECT_SELECTED, SUBOBJECT_CREATED. Они также видны в существующих логах UI.

## UNIQUE: изменение НЕ применено

Проверенная рабочая версия PostgreSQL: 18.6. Текущее ограничение:

```sql
UNIQUE (report_date, employee_id, object_id, po_id, category_id)
```

Один инженер в один день с одним назначением не может сохранить два разных
подобъекта. До отдельного решения сервер показывает причину и отказывает
второму сохранению; существующий факт не заменяется и не объявляется новым.
Конкурентный конфликт также возвращает HTTP 409 с откатом транзакции.

Предлагаемая семантика для отдельного согласования:

```sql
UNIQUE NULLS NOT DISTINCT
    (report_date, employee_id, object_id, subobject_id, po_id, category_id)
```

Разные подобъекты станут разными фактами. Повтор обычного объекта с NULL
останется дублем. Факт родителя без детализации и факт его подобъекта смогут
сосуществовать. Это явное изменение семантики журнала.

Безопасное внедрение после согласования: транзакционная замена ограничения
с прежним именем, обновление поиска дублей и проверок конфликтов в repository,
проверка NULL-дублей, конкурентного сохранения и сохранности истории.
Автоматического применения миграции или изменения UNIQUE на этапе 5 нет.
Поддержка нескольких подобъектов одного назначения в один день остаётся
заблокированной этим ограничением до отдельного согласования.
