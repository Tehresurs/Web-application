# Сотрудник при загрузке ЖД-билета

08.10.2026. Восстановлен сценарий создания сотрудника из существующей панели билета.

## Причина и исправление

Точное сопоставление ФИО в backend работало, но новая панель билета не содержала действия создания сотрудника и ручного выбора при неоднозначности. Теперь для EMPLOYEE_NOT_FOUND отображаются уведомление «Сотрудник не найден в базе данных», кнопка «Добавить сотрудника» и ручной выбор сотрудника. Похожие ФИО располагаются первыми, но автоматически не выбираются. Архивные сотрудники недоступны для выбора; автоматического восстановления архива нет.

Открывается существующий employeeModal, ФИО заполнено из билета. Должность обязательна в этом сценарии; телефон и экипаж необязательны. Используется прежний обработчик сохранения и POST /api/employees. Дополнительные поля существующей формы сохранены. ФИО сопоставляется по регистру и нормализованным пробелам без исправления букв.

После создания полученный ID сохраняется в контексте исходного билета и выполняется GET /api/rail-tickets/{id}. Подтверждение остаётся явным действием пользователя. Файл не загружается повторно, билет не создаётся заново. При отмене подтверждение не выполняется; при ошибке POST введённые данные и билет сохраняются. Перед созданием повторно читается справочник и проверяется точное совпадение; найденные записи предлагаются для выбора вместо дубля. Ошибка сохранения также обновляет варианты совпадений.

Существующий POST /api/rail-tickets/{id}/confirm дополнен необязательным employee_id для явного ручного выбора. Прежний запрос {} работает без изменений. Проверяются существование сотрудника и архив; если ФИО однозначно соответствует другому сотруднику, сервер отклоняет несовместимый ID. Проверки билета, маршрута, транзакция создания RAIL movement, повторное подтверждение и восстановление прежнего движения сохранены. Новых маршрутов и миграций нет.
