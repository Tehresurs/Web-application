# Сотрудники — состояния и отсутствия

Завершено 04.10.2026. Карточка сохранена, добавлена финальная доводка.

- Шапка: два индикатора — место работы и текущее состояние. Приоритет: существующая дата увольнения → активное отсутствие → существующий календарь дня. Неоднозначные или недоступные данные дают «Не определено». Несколько одновременных отсутствий показываются вместе. Границы периодов включительные.
- Основные данные: личные и рабочие параметры рядом на desktop; текущие дни включены в рабочие параметры и читаются из прежнего месячного ЛУВР.
- История: Прибыл / Убыл, история перемещений, отсутствия, согласованные исключения. Прежние формы движения и исключений сохранены.
- В «Отсутствиях» два варианта: «Другое» со свободной причиной/периодом/комментарием и «Уволен» с существующей `employees.dismissal_date`. Для увольнения используется прежний PATCH сотрудника; второй даты нет.
- Пустые будущие вкладки, экипаж, назначения и боковое меню сохранены.

## Хранение и совместимость

Миграция `012_employee_absences.sql` применена через `migrate_employee_absences.py` в транзакции. Создана `employee_absences` для новых периодов, с FK на сотрудника ON DELETE RESTRICT. Причины не являются enum: «Отпуск», «Обучение», «Больничный» и прочие значения — обычный текст.

Старые болезни остаются в `employee_sick_periods`, отображаются через объединённое чтение без копирования дат/периодов. Таблица `employee_sick_absence_labels` хранит только необязательную редактируемую подпись существующего больничного, по уникальному ID исходной записи. Удаление исходного периода удаляет только эту подпись. Структура и FK прежних таблиц не изменены. Runner сравнил старые значения больничных до/после миграции.

Новые «Другое» влияют на состояние карточки, но не участвуют в FINAL, месячных итогах, продолжительности или membership. Старые болезни продолжают участвовать в ЛУВР даже после изменения отображаемой причины — форма явно сообщает об этом. Явное изменение дат/удаление существующего больничного меняет ту же исходную запись, как прежний API; дубликата нет.

API в стиле существующего backend: GET/POST `/api/employees/{employee_id}/absences`, PATCH/DELETE `/api/employees/{employee_id}/absences/{source}/{item_id}`. `source` — внутреннее происхождение `other`/`sick`, не перечень пользовательских причин. POST создаёт только новое «Другое». Новым периодам необходима дата окончания; старые открытые больничные поддерживаются. Запись другого сотрудника изменить нельзя.
