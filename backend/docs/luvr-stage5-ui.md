# ЛУВР: единый блок, сортировка и закреплённая прокрутка

Выполнено 03.10.2026. Объединены два UI-дополнения к этапу 5. Backend, API и структура БД не менялись. Excel не формировался.

## Интерфейс

В боковой панели один пункт «ЛУВР». Он открывает последний выбранный экран модуля, по умолчанию месячный ЛУВР. Внутри — «ЖД-билеты», «ЛУВР», «Календарь ЛУВР». Активная вкладка выделена цветом и `aria-current`. Существующие элементы страниц и обработчики сохранены; переключение использует `showMainSection`, без перезагрузки приложения. При выходе в другой раздел внутренняя навигация скрывается.

ЖД-билеты продолжают использовать прежний upload/парсер/подтверждение; месячная таблица — прежний API состава и расчёта; индивидуальный календарь — прежний детальный расчёт. Новых бизнес-сущностей нет.

## Сортировка

Клик по заголовку переключает направление, стрелка и `aria-sort` показывают активную сортировку. По умолчанию ФИО А→Я. Поддерживаются ФИО, должность, специальность, место, график, состояние и четыре числовых итога (рабочие дни, Д, МВ, П).

Сортировка выполняется над копией массива уже загруженных сотрудников; строки и вложенные дни/итоги не перестраиваются по индексам. Все действия остаются привязаны к employee_id. № — визуальный номер после сортировки. Никаких запросов к API при сортировке нет.

Текст сравнивается русским `Intl.Collator`, ФИО — со схлопыванием пробелов. Пустые значения стабильно в конце при обоих направлениях. При равенстве — ФИО, затем ID. Числовые итоги сравниваются числами. Состояние использует рассчитанные данные: увольнение, болезнь, вахта, МВ, неизвестное состояние; для неприменимого 5/2 значение пустое.

Выбор сортировки сохраняется в состоянии frontend при переходах между вкладками и смене месяца. Перезагрузка страницы возвращает начальную сортировку. Горизонтальная позиция при сортировке сохраняется.

## Прокрутка

Таблица одна. Дополнительная нативная горизонтальная полоса внизу окна синхронизирована с её существующим scroll-container в обе стороны. Она показывается только при переполнении по ширине, когда таблица видима, а её настоящий нижний scrollbar — ниже экрана. У нижнего края таблицы, при отсутствии переполнения и при смене вкладки полоса скрывается.

№ и ФИО закреплены слева; смещение ФИО вычисляется по реальной ширине №. Настоящие ячейки заголовка используют `position: sticky`; их вертикальное смещение учитывает прокрутку страницы внутри горизонтального overflow-контейнера. Пересечения заголовка и первых двух колонок имеют непрозрачный фон и отдельные z-index.

Вертикальная прокрутка страницы остаётся обычной. Wheel/Shift+wheel не перехватываются. ResizeObserver следит за таблицей и контейнером, MutationObserver — за строками и видимостью вкладки; обновления объединяются через requestAnimationFrame. Ширина полосы вычисляется по фактическому scrollWidth, включая 28/29/30/31 дней.

## Проверки

- **296 backend-тестов** прошли, включая регрессию этапов 1–5, билетов, matching, защиты от дублей, истории, длительности и исключений.
- **152 frontend-теста** прошли, без пропусков, включая рекурсивный обход папок, действия с билетами, календарь, duration, сортировку и браузерную проверку общих модальных окон.
- `git diff --check` — ошибок нет.

Реальный Chrome, изолированная схема PostgreSQL, 72 сотрудника:

1. Нативное перетаскивание закреплённого scrollbar до конца календаря без вертикального сдвига страницы.
2. Синхронизация в обе стороны; обычное колесо прокручивает сотрудников.
3. №/ФИО и заголовок остаются видимыми; проверены координаты ячеек.
4. У настоящей нижней полосы дубликат скрывается, при возвращении выше появляется.
5. Проверены ширины окна 1100, 1366, 1600, 1920; при помещении таблицы целиком дополнительная полоса скрывается.
6. Настоящий клик мышью по 31 числу после прокрутки, сохранение П и возврат автоматического значения — успешно.
7. Смена месяцев 28/29/30/31: ширина полосы соответствует таблице.
8. Три вкладки работают без перезагрузки. Загрузка PDF, подтверждение RAIL, повторная загрузка как дубль и PDF с двумя билетами — успешно.
9. Все 10 полей сортировки в обоих направлениях: для каждой строки проверены employee_id, ФИО, все дни, итоги и состояние. Сортировка не отправляет запросов.
10. Горизонтальная позиция сохранена после сортировки; сортировка сохранена после посещения детального календаря.
11. После сортировки открыт правильный день правильного сотрудника. Сохранение/отмена override изменили только выбранную запись, остальные строки остались прежними.

Отдельный браузерный сценарий на рабочем сервере с **68 реальными сотрудниками** выполнен строго read-only: переходы вкладок, все поля сортировки и направления, идентичность всех данных строки, сохранение порядка после детального календаря. В рабочую БД тесты ничего не записывали. Ошибок JavaScript нет.

Команды браузерных сценариев (Chrome/CDP :9234; изолированный fixture-server :8881):

```powershell
node tests/browser/luvr_scroll.cjs
node tests/browser/luvr_navigation_sort.cjs
$env:LUVR_READONLY_URL='http://127.0.0.1:8000'
node tests/browser/luvr_navigation_sort.cjs
```

Сценарии без LUVR_READONLY_URL выполняют изменения только на изолированном сервере :8881 и требуют подготовленную длинную тестовую таблицу. Они не включены в обычный `tests/*.cjs`.
