## Архитектура

Браузер сотрудника → HTTPS Cloudflare Access → Tunnel → 127.0.0.1:18001
→ DemoAccess → приложение/данные версии 8001.

18001 — отдельный защищённый вход к тому же коду/схеме, не HTTP-прокси к
неограниченному 8001. Порт 18001 привязывается только к loopback.
Обычный 8001 сохраняет прежние права и не требует новой учётки.
Демо-вход не даёт роли руководителя ни одному удалённому запросу.

Аутентификация приложения — HTTP Basic, только за HTTPS при внешнем доступе.
Cloudflare Access дополнительно ограничивает конкретный email.
Приложение само проверяет username/password и не доверяет X-Role,
Cf-Access-Authenticated-User-Email или другим заголовкам как полномочиям.
JWT Access проверяет cloudflared через обязательный originRequest.access.
Две проверки независимы: email/OTP в Cloudflare и учётка просмотра приложения.

Учётки приложения хранятся вне Git: backend/private/demo_users.json.
Только роль READ_ONLY. Пароль не хранится открыто: PBKDF2-HMAC-SHA256,
800000 итераций, случайная соль 24 байта. Минимум 16 символов.
CLI не принимает пароль через аргументы/переменные окружения, использует getpass.
В Windows приватный каталог ограничивается текущей учёткой через icacls.
Есть ограничение неуспешных попыток и короткий кеш успешных проверок;
удаление пользователя/смена пароля сразу инвалидируют кеш.
HTTP Basic браузер может кешировать: для выхода закрыть приватное окно,
для немедленного отзыва удалить учётку командой revoke.

Защита:
- любой метод кроме GET/HEAD запрещён до прикладных обработчиков;
- GET разрешён только по проверенному allowlist, неизвестные маршруты запрещены;
- папки/обработка/публикация/экспорт новых файлов/API docs/чужие БД запрещены;
- роль READ_ONLY хранится в request-local ContextVar, не меняет общую роль;
- каждое DB-подключение просмотра — default_transaction_read_only=on и read_only=True;
- на подключении проверяется точное имя БД/схемы;
- блокировка FOR KEY SHARE при чтении истории пропускается только в этом контексте;
  обычные операции сохраняют прежние блокировки;
- HTML демо получает отдельный UI-guard: скрытые/отключённые действия записи,
  запрет клиентских write-fetch и предупреждение «Только просмотр»;
- навигация, фильтры, карточки, детализация, таблицы и SVG-графики сохранены;
- no-store, DENY framing, CSP с ресурсами только своего origin.

## Настроить Cloudflare без открытого промежутка

Все команды ниже — инструкция, не выполнялись в рамках проверки.

1. Установить cloudflared по официальной странице Downloads:
   https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/
2. В Cloudflare Zero Trust создать Self-hosted Access application для
   demo.ВАШ-ДОМЕН, защищающую все пути.
3. Политика Allow → Include → Emails → только email сотрудника.
   Не использовать Everyone или Bypass. Выбрать One-time PIN либо существующий IdP;
   убедиться, что доступ выдаётся именно этому email. Установить разумное время сессии.
4. Включить HTTPS/перенаправление HTTP→HTTPS для hostname (Always Use HTTPS).
5. Подготовить named Tunnel:

```powershell
cloudflared tunnel login
cloudflared tunnel create tehresurs-8001-view
Copy-Item backend/cloudflare/demo-8001.example.yml backend/cloudflare/demo-8001.yml
```

6. Заполнить UUID и путь credentials-file, hostname, teamName, audTag из
   Access application. originRequest.access.required должен оставаться true.
   Единственный service: http://127.0.0.1:18001, catch-all: http_status:404.
   Никогда не подставлять service 8001 или 8000.
7. До запуска проверить конфигурацию:

```powershell
cloudflared tunnel --config backend/cloudflare/demo-8001.yml ingress validate
cloudflared tunnel --config backend/cloudflare/demo-8001.yml ingress rule https://demo.ВАШ-ДОМЕН
```

8. Только после настройки Access, успешной локальной проверки и проверки allowlist:

```powershell
cloudflared tunnel route dns tehresurs-8001-view demo.ВАШ-ДОМЕН
cloudflared tunnel --config backend/cloudflare/demo-8001.yml run tehresurs-8001-view
```

9. Проверить с другого устройства:
   без авторизации интерфейс недоступен; чужой email не проходит Access;
   правильный email проходит OTP и затем HTTP Basic с учёткой просмотра;
   прямые POST/PATCH/DELETE дают 403, навигация/фильтры/графики работают.
   Отзыв учётки приложения немедленно закрывает доступ.
10. До завершения этой внешней проверки доступ нельзя считать проверенным через интернет.

Схема Access и обязательная проверка JWT соответствуют официальным документам:
- https://developers.cloudflare.com/cloudflare-one/access-controls/policies/
- https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/
- https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/#access
- https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/configuration-file/
